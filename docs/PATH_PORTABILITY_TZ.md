# ТЗ: устранение жёстких путей и зависимостей от расположения приложения

## Цель

Зафиксировать места проекта, которые связаны с путями приложения, системными каталогами или внешними исполняемыми файлами, и определить, что нужно изменить перед дальнейшей сборкой и распространением Jarvis.

Главная цель: Jarvis не должен зависеть от конкретного места установки, конкретной буквы диска или заранее известного пути к пользовательским приложениям.

---

## Результат анализа ветки `osnova`

В текущем коде **не обнаружен жёстко прописанный абсолютный путь вида `C:\\Jarvis`, `C:\\Users\\...` или `C:\\Program Files\\...` в рабочей логике приложения**.

При этом есть несколько мест, которые нужно считать критичными для проверки и дальнейшего рефакторинга. Часть из них уже реализована правильно, а часть пока зависит от внешнего окружения Windows.

Важно: строки `C:\\Jarvis` и `D:\\Apps\\Jarvis` в `README.md` являются только примерами документации и не используются как реальные пути приложения.

---

## 1. `core/app_paths.py` — основной механизм определения пути

Файл: `core/app_paths.py`

Текущая логика:

- в режиме исходников корень определяется относительно `__file__`;
- в frozen-сборке корнем считается каталог рядом с реально запущенным `.exe` через `sys.executable`;
- ресурсы учитывают `sys._MEIPASS` PyInstaller;
- `workspace` и `logs` строятся относительно `APP_ROOT`;
- пользовательские настройки строятся относительно `%APPDATA%`.

Текущие пути:

```text
APP_ROOT/
├── workspace/
├── logs/
└── ...

%APPDATA%/Jarvis/
└── settings.json
```

### Статус

**Уже сделано правильно.** Жёсткий путь к месту установки отсутствует.

### Что сделать дальше

Не возвращать абсолютные пути в код. Все внутренние пути приложения должны строиться через централизованный модуль `core/app_paths.py`.

При добавлении новых каталогов запрещается писать конструкции вроде:

```python
Path("C:\\Jarvis\\...")
```

Вместо этого использовать `APP_ROOT`, `RESOURCE_ROOT`, `APP_DATA_DIR` и отдельные централизованные константы/функции.

## 2. `tools/applications.py` — поиск установленных приложений

Файл: `tools/applications.py`

Здесь используются системные каталоги Windows:

```text
%APPDATA%\\Microsoft\\Windows\\Start Menu\\Programs
%PROGRAMDATA%\\Microsoft\\Windows\\Start Menu\\Programs
```

Это **не жёсткие пользовательские пути**, поскольку они строятся через переменные окружения `APPDATA` и `PROGRAMDATA`.

Также используется:

```python
shutil.which(...)
```

для поиска `.exe` через `PATH`.

### Статус

**В целом правильно**, но этот модуль критичен для будущей переносимости.

### Что изменить в будущем

Создать отдельный слой `Application Resolver`, который будет возвращать единую структуру приложения:

```text
Application Identity
├── display_name
├── executable_path
├── launcher_path
├── working_directory
└── arguments
```

Поиск должен происходить через несколько источников, а не через заранее известные пути:

1. Start Menu;
2. `PATH`;
3. зарегистрированные приложения Windows, если потребуется;
4. пользовательские алиасы;
5. дополнительные источники, добавляемые позже.

Нельзя добавлять конструкции вида:

```text
Discord -> C:\\...
Steam -> C:\\...
Prism Launcher -> C:\\...
```

как основной механизм поиска.

## 3. `core/ollama_manager.py` — внешняя Ollama

Файл: `core/ollama_manager.py`

Jarvis запускает Ollama так:

```python
subprocess.Popen(["ollama", "serve", ...])
```

То есть путь к `ollama.exe` **не прописан вручную**. Windows должна найти его через `PATH`.

Одновременно адрес API по умолчанию:

```text
http://localhost:11434
```

задаётся как URL сервера Ollama, а не как путь к файлу.

### Статус

**Жёсткого пути к `ollama.exe` нет.**

### Что изменить в будущем

Добавить нормальный resolver внешних зависимостей:

```text
Dependency Resolver
├── Ollama executable
├── Python/runtime (если потребуется)
└── другие внешние компоненты
```

Для Ollama желательно:

1. сначала искать `ollama` через `PATH`;
2. при необходимости проверять стандартные места установки Windows через системные механизмы, а не через один конкретный абсолютный путь;
3. позволить пользователю указать собственный путь в настройках;
4. хранить пользовательский путь в `%APPDATA%\\Jarvis\\settings.json`.

Это особенно важно для будущего `.exe` и установки на другой компьютер.

## 4. `config/settings.json` — адрес Ollama

Файл: `config/settings.json`

Сейчас задано:

```json
"ollama": {
  "base_url": "http://localhost:11434"
}
```

Это допустимо как значение по умолчанию для локальной Ollama.

### Что сделать

Оставить `localhost:11434` дефолтным значением, но не считать его единственно возможным адресом.

В настройках приложения должен существовать изменяемый `base_url`.

Это не проблема переносимости файлов, но это внешний адрес зависимости, поэтому он также должен оставаться конфигурируемым.

## 5. `start.bat` — запуск из каталога самого проекта

Файл: `start.bat`

Используется:

```bat
cd /d "%~dp0"
start "" pythonw main.py
```

Это правильно: `%~dp0` означает каталог самого `.bat`, поэтому запуск не зависит от того, где находится проект.

### Статус

**Уже сделано правильно.**

Не заменять `%~dp0` на конкретный путь.

## 6. `README.md` — примеры путей

Файл: `README.md`

В документации встречаются:

```text
C:\\Jarvis
D:\\Apps\\Jarvis
```

Это только демонстрация переносимости и не является рабочей конфигурацией.

### Статус

**Изменять код из-за этих строк не требуется.**

При дальнейшем редактировании документации желательно явно сохранять их как примеры, чтобы никто не воспринял их как обязательные пути установки.

# Что именно нужно изменить перед финальной сборкой

## Приоритет 1 — централизованные пути

Все новые пути должны проходить через `core/app_paths.py`.

Нельзя создавать новые абсолютные пути в отдельных модулях.

Рекомендуемые централизованные значения:

```text
APP_ROOT
RESOURCE_ROOT
WORKSPACE_DIR
LOG_DIR
APP_DATA_DIR
CONFIG_FILE
```

При необходимости добавить туда новые каталоги, например:

```text
CACHE_DIR
MODELS_DIR
TEMP_DIR
```

а не создавать их вручную в разных файлах.

## Приоритет 2 — resolver внешних приложений

Доработать `tools/applications.py` в полноценный `Application Resolver`.

Jarvis должен находить приложения по имени, а не знать заранее, где конкретно пользователь их установил.

## Приоритет 3 — resolver внешних зависимостей

Для Ollama и будущих внешних компонентов не использовать абсолютные пути, зашитые в код.

Использовать:

```text
PATH
→ системный поиск
→ пользовательская настройка
→ понятная ошибка
```

## Приоритет 4 — тест переноса

Перед сборкой `.exe` обязательно проверить сценарий:

```text
C:\\Jarvis
    ↓ перенос
D:\\Test\\Jarvis
    ↓ запуск
```

И отдельно:

```text
C:\\Users\\User\\Desktop\\Jarvis
    ↓ перенос
E:\\Apps\\Jarvis
    ↓ запуск
```

Jarvis должен:

- запускаться;
- создавать `workspace`;
- создавать `logs`;
- находить конфигурацию;
- работать с sandbox;
- находить Ollama без привязки к конкретному пути;
- не требовать изменения исходного кода после переноса.

# Итог

На текущий момент **критического hardcode пути установки Jarvis в рабочем коде не найдено**. Основная архитектура путей уже сделана переносимой.

Критические файлы для дальнейшего контроля:

| Файл | Назначение | Статус |
|---|---|---|
| `core/app_paths.py` | Пути самого Jarvis | Уже сделано правильно |
| `tools/applications.py` | Поиск Windows-приложений | Нужен дальнейший Application Resolver |
| `core/ollama_manager.py` | Поиск/запуск Ollama | Нет hardcode, нужен Dependency Resolver |
| `config/settings.json` | Настройки Ollama | `localhost:11434` оставить конфигурируемым |
| `start.bat` | Запуск проекта | Уже переносимый |
| `README.md` | Примеры путей | Только документация |

Этот документ является **ТЗ на предотвращение появления новых жёстких путей**, а не требованием немедленно переписывать перечисленные файлы. Перед финальной сборкой `.exe` нужно отдельно пройтись по каждому пункту и проверить его реальной установкой на другом пути/диске.
