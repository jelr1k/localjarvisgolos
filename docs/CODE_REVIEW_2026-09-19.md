# Результаты ревью Jarvis от 2026-09-19

## Назначение
Сводка ревью Claude и последующего разбора с учётом реального сценария использования Jarvis. Документ разделяет замечания на: исправить сейчас, сделать следующим этапом, оставить техническим долгом и не делать пока.
Проект сейчас рассчитан на локальное использование автором, другом и небольшим кругом знакомых. В будущем планируется расширение возможностей агента за пределы текущего Workspace.

# 1. Исправить в первую очередь

## 1.1 Command Router: fallback в LLM
Router может перехватывать обычную речь только потому, что сообщение начинается с известного глагола. Примеры: «Найди мне рецепт борща» может стать поиском файла, а «Убери пробелы из текста» может стать удалением файла.
Решение: Router выполняет действие только при уверенном совпадении. Если цель не найдена или уверенность недостаточна, передавать фразу в LLM: Router -> None -> LLM.
Приоритет: высокий. Проблема уже проявлялась в реальном использовании.

## 1.2 close_application: подтверждение и защита процессов
Проблема: закрытие приложения может выполняться без подтверждения, а после таймаута процесс может быть принудительно завершён.
Риски: потеря несохранённых данных, случайное закрытие Ollama, потенциальное закрытие самого Jarvis или важных процессов, ошибки распознавания голосовой команды.
Решение: вернуть подтверждение, защитить Jarvis и критичные процессы, отдельно учесть Ollama, предпочитать корректное завершение и использовать принудительное завершение только как fallback.
Приоритет: высокий.

## 1.3 TTL для pending launch choices
После неоднозначного запуска состояние выбора может сохраняться слишком долго. Сообщение «2» спустя время не должно запускать старый вариант.
Решение: добавить срок жизни состояния, например несколько десятков секунд, после чего выбор автоматически сбрасывается.
Приоритет: высокий/средний.

## 1.4 CI и тесты
Часть тестов написана в стиле pytest, но CI использует unittest discover. По ревью часть тестов может вообще не выполняться. CI также должен устанавливать зависимости, необходимые тестам.
Решение: перейти CI на pytest, установить зависимости, при необходимости использовать Windows runner для Windows/PySide6/WinAPI-зависимостей, проверить запуск всех тестов, добавить тесты для close_application и несоответствия подтверждённого пути удаления.
Приоритет: высокий.

## 1.5 Логирование
Несколько лог-файлов создаются, но значительная часть сообщений попадает в один файл. Подробные DEBUG-логи нужны для разработки, поэтому их не следует просто удалять.
Целевая структура: jarvis.log — общие события; errors.log — ошибки; llm.log — LLM и генерация; tools.log — инструменты; voice.log — аудио и Whisper.
INFO должен быть обычным режимом. DEBUG должен оставаться доступным для диагностики. Для одного файла должен использоваться один корректный handler.
Приоритет: высокий/средний.

# 2. Следующим этапом

## 2.1 Скользящее окно истории LLM
История не должна расти бесконечно. Ограничивать её количеством сообщений или токенов.
Приоритет: средний/высокий.

## 2.2 Неблокирующий запуск Ollama
Проблема по ревью: запуск Ollama может блокировать создание UI. Исправление не означает, что Ollama должна оставаться запущенной после закрытия Jarvis.
Требование проекта сохраняется: если Ollama должна быть выключена, она должна быть выключена; модель при закрытии Jarvis выгружается; уже запущенный сервер не обязан сохраняться.
Цель только в том, чтобы запуск сервера происходил в фоне и не замораживал интерфейс.
Приоритет: средний.

## 2.3 Подтверждение удаления: фиксировать конкретный путь
В LLM-пути модель может передать нечёткий путь, а fuzzy search выполняется после подтверждения. Тогда пользователь потенциально подтверждает один объект, а удаляется другой.
Правильный порядок: LLM предлагает путь -> Jarvis разрешает и находит конкретный объект -> пользователь видит конкретный объект -> подтверждает его -> операция выполняется по уже разрешённому пути без нового fuzzy search.
Приоритет: средний. Router уже работает ближе к правильной схеме.

## 2.4 Объединить архитектуру close_application
Сейчас есть реализация через pywin32 и рабочая реализация через shell. Не удалять рабочий вариант только ради формального устранения дублирования. Сначала сделать один публичный close_application, а конкретные механизмы оформить как основную реализацию и fallback/эксперимент.
Приоритет: средний.

# 3. Технический долг, пока не мешает работе

## 3.1 Создание и запуск исполняемых файлов
Claude отметил, что модель теоретически может создать bat/cmd/vbs/js и затем запустить его через инструменты.
Это реальная архитектурная граница безопасности, но сейчас риск ограничен локальным сценарием и отсутствием доступа модели к недоверенному интернет-контенту или чужим документам.
Сейчас не блокировать разработку. При расширении агента за пределы Workspace, добавлении интернета, внешних документов или более автономного выполнения задач пересмотреть запрет создания исполняемых расширений, подтверждение запуска скриптов и отдельные разрешения на выполнение кода.
Приоритет сейчас: низкий.

## 3.2 Router и индекс вне UI-потока
Обновление индекса и нечёткий поиск могут выполнять тяжёлые операции в UI-потоке. При увеличении количества файлов и приложений это может вызывать подвисания.
Приоритет: средний/низкий, особенно до Workspace 2.0.

## 3.3 Пересоздание Whisper при apply_config
Если SpeechRecognizer пересоздаётся при каждом применении настроек, это лишняя работа. В будущем пересоздавать Whisper только при изменении модели, устройства или вычислительного режима.
Если текущая задержка не ощущается, исправление не срочное.
Приоритет: низкий.

## 3.4 chunk_size=1 и потоковая генерация
Потоковая генерация является намеренной частью UX: ответ должен поступать небольшими частями и постепенно появляться в UI.
Замечание Claude относится к эффективности чтения HTTP-потока, а не к необходимости отказаться от потоковой генерации. В будущем можно оптимизировать чтение без изменения поведения UI.
Приоритет: низкий.

## 3.5 Английские инструменты
Поддержка английских запросов сейчас не является требованием. Jarvis ориентирован на русский язык.
Сейчас не исправлять.

## 3.6 Мёртвый и заготовочный код
Часть найденного кода действительно не используется, но часть оставлена как заготовка на будущее. Не удалять автоматически. При рефакторинге разделить реально устаревший код и запланированные заготовки.
Приоритет: низкий.

# 4. Голосовой ввод
Качество Whisper сейчас является реальной пользовательской проблемой: распознавание может неправильно передавать названия файлов, приложений и отдельные слова.
Проверять весь пайплайн: микрофон -> частота дискретизации -> каналы -> нормализация -> ресемплинг -> Whisper -> initial prompt -> постобработка -> Router.
Отдельно проверить качество ресемплинга и вариант resample_poly, а также передачу имён приложений и алиасов в initial prompt.
Приоритет: средний/высокий, потому что проблема уже заметна в реальном использовании.

# 5. Workspace 2.0
Будущая цель: перейти от Workspace как папки с вручную добавляемыми объектами к управляемому индексу доступных файлов и приложений.
При первом запуске или отдельном сканировании Jarvis сможет обнаруживать приложения и другие объекты, сохранять пути и показывать пользователю список.
Пользователь сможет включать/выключать объект, удалять его из индекса, добавлять вручную, настраивать алиасы и повторно сканировать систему.
Желательно иметь отдельный индекс приложений, чтобы Router не выполнял полный поиск файловой системы на каждый запрос.
Для обнаружения приложений в будущем рассмотреть меню Пуск, зарегистрированные приложения Windows, стандартные каталоги установки, PATH и ручное добавление. Не делать бездумный полный rglob всего диска.
Приоритет: отдельный будущий этап.

# 6. Документация
Текущее количество документации и её расхождение с кодом признаны отдельной проблемой.
Цель: один актуальный источник информации для каждой категории.
Предварительная структура: README.md — назначение и быстрый запуск; docs/TZ_JARVIS.md — актуальные требования и задачи; docs/ARCHITECTURE.md — архитектура; отдельные документы только для самостоятельных больших тем.
Справочник команд в будущем желательно строить непосредственно из кода, чтобы он не расходился с реальными алиасами и инструментами.
Приоритет: высокий как задача по организации проекта.

# 8. Главный вывод
Ревью Claude не означает, что архитектуру Jarvis нужно переписывать. Основные реальные проблемы сосредоточены в маршрутизации естественной речи, управлении процессами, тестовой инфраструктуре, логировании, контексте LLM и организации документации.
Базовые сильные стороны проекта сохраняются: разделение слоёв, централизованный ToolExecutor, повторная проверка разрешений, sandbox, проверка результатов файловых операций, атомарная запись конфигурации, потоковая генерация, отдельное управление Ollama и автоматическое определение корня приложения.
Этот документ является рабочим списком для последующей организации задач, а не обязательством выполнить каждый пункт подряд.
