# Актуальное ТЗ проекта Jarvis

**Версия документа:** 2.1  
**Дата обновления:** 2026-09-15  
**Проект:** локальный голосовой/текстовый ассистент Jarvis для Windows 11  
**Стек:** Python, PySide6, Ollama, локальные LLM, в будущем Whisper  
**Репозиторий:** `jelr1k/localjarvisgolos`  
**Основная ветка разработки:** `satichik-dev`

> Этот документ одновременно фиксирует фактически реализованное состояние проекта и оставшиеся этапы разработки. Реализованные пункты помечены как **ГОТОВО**, незавершённые — как **В РАБОТЕ / ПЛАН**.

## 0. Текущее состояние проекта

### 0.1. Базовая архитектура — ГОТОВО

В проекте уже реализованы и используются:

- автоматическое определение корня Jarvis;
- автоматическое создание необходимых рабочих директорий;
- переносимость рабочих путей;
- пользовательские настройки;
- sandbox и базовый слой безопасности;
- безопасная работа с путями;
- файловые инструменты;
- инструменты управления приложениями;
- обработка Windows-ярлыков;
- проверки фактического результата операций;
- управление локальным Ollama из UI;
- загрузка и выгрузка модели;
- отдельное отображение состояния сервера и модели;
- логирование;
- фоновые задачи мониторинга;
- потоковый вывод ответа.

### 0.2. Command Router — ГОТОВО

Пользовательский текст проходит через `CommandRouter` до обращения к LLM.

Поддерживается разделение на:

```text
Пользовательский ввод
        ↓
Command Router
        ├─ простая однозначная команда → прямой инструмент
        └─ сложная/составная задача → LLM + необходимые tools
```

Реализованы прямые сценарии, включая запуск и закрытие приложений, проверку состояния процессов, поиск файлов, чтение файлов и другие поддерживаемые действия.

Router также корректно обрабатывает общие запросы вроде «закрой приложение», не пытаясь использовать слово «приложение» как конкретное имя программы.

### 0.3. Обычный чат и tools — ГОТОВО

Обычный разговор не получает полный набор доступных инструментов.

Для каждого запроса формируется ограниченный набор tools. Например:

- поиск → `search_files`;
- чтение → `read_file`;
- закрытие → `close_application`, `get_process_status`;
- запуск → `launch_application`, `get_process_status`;
- удаление → `delete_file`, `search_files`;
- обычный разговор → `tools=[]`.

Это снижает вероятность того, что модель самостоятельно вызовет системный или файловый инструмент без соответствующего намерения пользователя.

### 0.4. Составные команды — ГОТОВО

Router не обрывает составную команду на первом найденном действии.

Например:

```text
Найди файл tool_test.txt, прочитай его и перескажи своими словами
```

определяется как задача, содержащая как минимум:

```text
search → search_files
read   → read_file
```

Оба инструмента передаются модели для выполнения последовательности действий.

### 0.5. Multi-round Tool Calling — ГОТОВО

Реализован цикл:

```text
сообщение
   ↓
LLM
   ↓
tool call
   ↓
ToolExecutor
   ↓
результат
   ↓
LLM
   ↓
следующий tool call / финальный ответ
```

`GenerationWorker` поддерживает до 5 последовательных раундов Tool Calling. После каждого вызова результат возвращается в контекст модели.

### 0.6. Безопасность Tool Calling — ГОТОВО

`GenerationWorker` передаёт `ToolExecutor` только инструменты, разрешённые для текущего запроса.

Дополнительно сохраняются:

- проверки включённых инструментов;
- проверки разрешений;
- sandbox;
- подтверждение опасных операций;
- защита от вызова инструмента, который не входит в текущий scope.

### 0.7. Работа с файлами — ГОТОВО

Реализованы поиск и чтение файлов с учётом sandbox и разрешённых корней поиска.

Поддерживается сохранение неоднозначности: если найдено несколько одинаковых имён, Jarvis не должен автоматически выбирать случайный файл.

При обычном чтении содержимое может быть показано без обязательного вывода полного системного пути.

### 0.8. Логирование — ГОТОВО

Логи позволяют диагностировать:

- пользовательское сообщение;
- результат Router;
- выбранные tools;
- раунды генерации;
- tool calls;
- результаты инструментов;
- завершение или ошибку генерации.

### 0.9. Автоматические тесты — ГОТОВО

В проект добавлены тесты для:

- выбора tool scope;
- обычного чата без tools;
- поиска и чтения файлов;
- составных команд;
- подтверждений опасных операций;
- защиты `ToolExecutor`;
- многораундового Tool Calling;
- инструментов приложений;
- sandbox;
- файловых инструментов.

Текущий локальный результат запуска `run_tests.bat`:

```text
40 passed, 1 skipped
```

Для запуска тестов создан `run_tests.bat`.

# 1. Следующий этап: маршрутизация между несколькими моделями — ПЛАН

Полноценного отдельного `Model Router` в проекте пока нет.

Сейчас `ChatRequest` получает модель из текущей конфигурации, то есть выбор модели ещё не определяется автоматически сложностью задачи.

Необходимо реализовать отдельный слой выбора модели.

## 1.1. Цель

Jarvis должен автоматически выбирать подходящую локальную модель в зависимости от задачи.

Пример:

```text
Пользователь
      ↓
Command Router
      ↓
определение сложности / типа задачи
      ↓
Model Router
      ├─ быстрая модель
      ├─ основная reasoning-модель
      ├─ модель для кода
      └─ модель для Tool Calling
      ↓
Ollama
```

## 1.2. Факторы выбора

Model Router должен учитывать:

- количество действий;
- наличие нескольких объектов;
- сложность и неоднозначность формулировки;
- необходимость контекста диалога;
- необходимость Tool Calling;
- тип задачи;
- наличие прямого обработчика;
- доступность конкретной модели.

## 1.3. Fallback

Если выбранная модель недоступна, Jarvis должен уметь перейти к резервной модели.

```text
выбрана модель A
      ↓
A недоступна
      ↓
модель B
      ↓
B недоступна
      ↓
стандартная модель
```

Модели и их роли желательно хранить в конфигурации, а не жёстко прописывать в коде.

# 2. Дополнительное усиление Tool Calling — ПЛАН

Основная цепочка Tool Calling уже работает, поэтому дальнейшая задача — не реализовывать её заново, а расширять покрытие сложных сценариев.

Необходимо проверить цепочки вида:

```text
найти → прочитать → проанализировать
найти → открыть → проверить состояние → сообщить результат
создать → записать → прочитать → проверить
найти несколько объектов → выбрать нужный → выполнить действие
```

Отдельно проверить, что новый независимый запрос не продолжает незавершённую инструментальную задачу предыдущего сообщения.

# 3. Голосовое управление — ПЛАН

## 3.1. Локальное распознавание речи

Добавить Whisper или совместимое локальное решение:

```text
Микрофон
   ↓
Whisper
   ↓
текст
   ↓
Command Router
   ↓
инструмент / LLM
```

Распознавание должно выполняться локально.

## 3.2. Wake word

Добавить настраиваемое ключевое слово.

По умолчанию:

```text
Jarvis
```

Пользователь должен иметь возможность изменить его.

## 3.3. Режим активации

Предусмотреть режимы:

- только после wake word;
- обработка каждой распознанной фразы.

По умолчанию использовать wake word.

## 3.4. Защита от случайной активации

Фоновая речь, звук игр, Discord и обычный разговор не должны превращаться в команды без выполнения условий активации.

# 4. Голосовой ответ / TTS — ПЛАН

Добавить локальный синтез речи:

```text
команда
   ↓
обработка
   ↓
текстовый ответ
   ↓
TTS
   ↓
голос Jarvis
```

Настройки:

- включение/выключение;
- голос;
- скорость;
- громкость.

---

# 5. Юмор и характер Jarvis — ПЛАН

Добавить настраиваемую вероятность юмористической реплики.

Требования:

- `0%` полностью отключает эффект;
- вероятность задаётся пользователем;
- юмор не мешает выполнению команды;
- юмор не заменяет сообщения об ошибках;
- фразы не должны нарушать основную логику ассистента.

# 6. Подготовка конечной сборки `.exe` — ПЛАН

Необходимо подготовить конечную Windows-сборку.

Требования:

- запуск без ручного CMD;
- включённый Python runtime и необходимые зависимости;
- корректное определение корня приложения;
- переносимость между дисками;
- сохранение пользовательских настроек;
- работа sandbox и инструментов;
- работа Ollama;
- отсутствие зависания GUI;
- корректное завершение приложения.

Для режима исходников `start.bat` должен проверять и устанавливать зависимости из `requirements.txt`. Для готового `.exe` отдельная установка Python-зависимостей не требуется.

## 10. Критерии готовности текущего этапа

Текущий этап Command Router + Tool Calling считается рабочим, если:

- обычный чат не получает инструменты;
- простые команды могут выполняться напрямую;
- составная команда получает необходимые tools;
- ToolExecutor не разрешает инструмент вне текущего scope;
- опасные операции требуют подтверждения;
- несколько tool-call раундов выполняются последовательно;
- результат инструментов возвращается модели;
- пользователь получает финальный ответ, а не внутренние JSON-инструкции;
- тестовый набор проходит без ошибок.

Фактическая проверка на текущем этапе:

```text
40 passed, 1 skipped
```
