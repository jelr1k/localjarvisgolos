# Техническое задание проекта Jarvis

**Версия документа:** 1.0  
**Дата:** 2026-09-11  
**Проект:** локальный голосовой/текстовый ассистент Jarvis для Windows 11  
**Основной стек:** Python, PySide6, Ollama, локальные LLM, в будущем Whisper  
**Репозиторий:** `jelr1k/localjarvisgolos`

## 1. Назначение проекта

Jarvis — локальное настольное приложение-ассистент для Windows 11, которое принимает текстовые и в будущем голосовые команды, понимает естественные формулировки, выбирает подходящий способ обработки и выполняет действия через контролируемый набор инструментов.

Ключевой принцип проекта: языковая модель не получает прямой произвольный доступ к файловой системе или командной строке. Она формирует запрос к инструменту, а выполнение проходит через отдельный слой валидации, разрешений и проверки результата.

## 2. Цели первой очереди

1. Сделать надёжное ядро работы с файлами внутри жёстко ограниченной рабочей папки.
2. Автоматически определять расположение Jarvis без жёстко зашитых путей.
3. Расширять набор инструментов постепенно, сохраняя предсказуемость и безопасность.
4. Улучшить поиск файлов и обработку естественных формулировок.
5. Исправить ложные сообщения об успешном удалении и ошибки выбора ярлыка/исполняемого файла.
6. Синхронизировать имя ассистента с названием окна приложения.
7. Добавить управление Ollama Server кнопками в интерфейсе.
8. Подготовить архитектуру к голосовому управлению, нескольким моделям и сборке в `.exe`.

## 3. Целевая архитектура

```text
Ввод текста/голоса
        ↓
Whisper (в будущем для голоса)
        ↓
Command Router
        ├─ простая однозначная команда → прямой инструмент без LLM
        ├─ лёгкая команда → небольшая модель
        └─ сложная/неоднозначная команда → мощная модель Qwen
        ↓
Tool Executor
        ↓
Проверка разрешений и sandbox
        ↓
Выполнение действия
        ↓
Проверка фактического результата
        ↓
Ответ пользователю
```

Рекомендуемое разделение каталогов:

```text
app/
ui/
core/
llm/
ollama/
commands/
tools/
filesystem/
security/
workspace/
tests/
config/
```

## 4. Жёсткая sandbox-папка

### 4.1. Основное требование

Все файловые операции Jarvis по умолчанию выполняются только внутри одной рабочей папки проекта. Ограничение должно обеспечиваться кодом и слоем инструментов, а не только системной инструкцией для модели.

Подконталоги внутри рабочей папки разрешены. Выход за пределы рабочей папки запрещён для операций:

- чтение;
- создание;
- запись и изменение;
- удаление;
- поиск;
- переименование;
- перемещение;
- копирование;
- запуск файловых артефактов;
- получение информации о файлах.

### 4.2. Автоопределение расположения

Нельзя использовать постоянный путь вроде `C:\JARVIS\workspace`.

Jarvis должен:

1. определить фактическое расположение запускаемого приложения/проекта;
2. найти корень Jarvis относительно этого расположения;
3. получить рабочую папку из корня приложения по согласованному правилу;
4. одинаково работать после перемещения проекта или будущего `.exe` на другой диск и в другую папку.

Поддерживаемые сценарии:

- проект находится на `C:`;
- проект находится на `D:` или `E:`;
- проект вложен в другую папку;
- приложение запущено из исходников;
- приложение запущено как собранный `.exe`.

Рекомендуется разделить:

- **корень приложения** — место размещения кода/`.exe`;
- **рабочую папку** — папка, доступная файловым инструментам;
- **пользовательские настройки** — `%APPDATA%\Jarvis\`, чтобы они не зависели от расположения проекта.

### 4.3. Защита от обхода

Проверка безопасного пути должна учитывать:

- относительные переходы `..`;
- абсолютные пути Windows;
- разные разделители `\\` и `/`;
- символические ссылки;
- junction/reparse point;
- попытки передать путь к другому диску;
- нормализацию регистра и разрешение пути.

После нормализации итоговый путь обязан находиться внутри разрешённого корня. При нарушении операция блокируется до выполнения.

## 5. Слой безопасности и разрешений

Нужны отдельные компоненты:

- `security/sandbox.py` — определение и проверка корня;
- `security/validator.py` — валидация входных путей и параметров;
- `security/permissions.py` — включённые функции и подтверждения;
- `tools/executor.py` — единая точка запуска инструментов.

Модель не должна вызывать произвольные `cmd`, PowerShell или shell-команды на раннем этапе. Вместо этого используются узкие инструменты с понятными параметрами.

Для действий вне sandbox требуется отдельный режим системного доступа, не смешанный с файловым режимом проекта. Он должен быть выключен по умолчанию и состоять из отдельных разрешений, например:

- запуск приложений;
- поиск установленных приложений;
- проверка запущенных процессов;
- закрытие приложений;
- открытие URL;
- доступ к настройкам Windows.

Произвольное чтение/изменение файлов за пределами рабочей папки и произвольный shell-доступ в первой версии не допускаются.

## 6. Расширение инструментов

Расширять набор инструментов поэтапно, с тестами и проверкой фактического результата.

### 6.1. Файловые инструменты

Базовый набор:

- `search_files` — поиск по имени, расширению и подкаталогам;
- `read_file` — чтение текстового файла;
- `create_file` — создание файла;
- `write_file` — запись/перезапись;
- `delete_file` — удаление с верификацией;
- `rename_file` — переименование;
- `copy_file` — копирование;
- `move_file` — перемещение;
- `create_folder` — создание папки;
- `file_info` — размер, тип, дата изменения, существование.

Каждый инструмент обязан:

1. проверить, что он включён в настройках;
2. проверить параметры;
3. проверить sandbox;
4. выполнить действие;
5. проверить состояние после действия;
6. вернуть структурированный результат с `success`, `error`, `path`, `details`.

### 6.2. Инструменты приложений

Разрешённый безопасный минимум:

- `launch_application`;
- `find_application`;
- `get_process_status`;
- `close_application` с отдельным подтверждением;
- `open_url`.

Запуск приложения должен выполняться через конкретный инструмент, а не через универсальный запуск произвольной команды.

## 7. Поиск файлов и естественные формулировки

### 7.1. Поиск без полного пути

Пользователь не обязан указывать полный путь. Jarvis должен искать по имени в рабочей папке и её подкаталогах.

Нужно поддержать:

- точное имя;
- имя без расширения;
- совпадение по stem;
- поиск с учётом регистра без требования к регистру;
- несколько кандидатов с отчётом об неоднозначности;
- явное указание расширения.

### 7.2. Семантика типов файлов

Система обязана различать тип цели:

- «ярлык Discord» → предпочтительно `Discord.lnk`;
- «ярлык Prism Launcher» → предпочтительно `Prism Launcher.lnk`;
- явное «Discord.exe» → искать именно `Discord.exe`;
- явное «файл Discord» без типа → искать все подходящие варианты;
- несколько совпадений → не выбирать случайный файл, а вернуть неоднозначность.

Нельзя подменять запрос на ярлык ближайшим `.exe`.

### 7.3. Синонимы и варианты команд

Нужен слой алиасов и интентов, чтобы понимать естественные формулировки:

- «удали» / «стереть» / «убери»;
- «покажи» / «найди» / «открой»;
- «ярлык» / «ссылка»;
- «приложение» / «программа»;
- разговорные и сокращённые варианты названий.

Логика выбора цели должна учитывать одновременно действие, объект и тип объекта.

## 8. Исправление удаления и ложного успеха

### 8.1. Фактическое удаление

`delete_file` должен реально вызвать удаление файла и не возвращать успех заранее.

Алгоритм:

1. разрешить имя через безопасный резолвер;
2. проверить, что найден именно нужный тип объекта;
3. выполнить удаление;
4. проверить `Path.exists() == False`;
5. только после этого вернуть `success: true`.

### 8.2. Ошибки

При `PermissionError`, `OSError`, блокировке файла или другой ошибке:

- вернуть `success: false`;
- указать реальную причину;
- не писать пользователю, что файл удалён;
- не маскировать исключение общим «готово».

### 8.3. Ярлыки

Файл `.lnk` должен удаляться как обычный файл ярлыка. Работа запущенного приложения, на которое он указывает, не должна мешать удалению самого ярлыка.

## 9. Синхронизация имени ассистента и названия приложения

В настройках требуется единое предсказуемое поведение.

Минимальный вариант:

- поле «Имя ассистента» используется в сообщениях, приветствиях и названии окна.

Допустимый расширенный вариант:

- «Имя ассистента» — имя персонажа;
- «Название приложения» — заголовок окна и отображаемое имя программы.

Если используется одно поле, при изменении имени необходимо обновлять:

- заголовок главного окна;
- подписи интерфейса, где отображается имя;
- приветствие;
- будущие уведомления.

Имя пользователя не должно автоматически менять имя `.exe` во время работы приложения. Переименование файла сборки является отдельным этапом упаковки.

## 10. Управление Ollama Server из интерфейса

В интерфейсе должна быть отдельная зона управления Ollama.

### 10.1. Кнопки

Минимум:

- «Запустить Ollama Server»;
- «Остановить Ollama Server»;
- «Обновить статус»;
- «Загрузить модель»;
- «Выгрузить модель».

### 10.2. Отображаемые состояния

Нужно различать:

1. сервер остановлен;
2. сервер запущен;
3. модель не загружена;
4. модель загружена;
5. идёт генерация;
6. ошибка подключения;
7. выполняется запуск/остановка.

Состояния сервера и модели не должны смешиваться в один флаг.

### 10.3. Поведение при закрытии Jarvis

Предпочтительное поведение:

- закрытие GUI не завершает Ollama Server автоматически;
- активная модель выгружается корректно, если это предусмотрено текущей логикой;
- сервер продолжает работать до ручной остановки или отдельной настройки.

Приложение должно проверять, запущен ли сервер уже, и не запускать второй экземпляр без необходимости.

## 11. Command Router и выбор уровня обработки

Команды разделяются по сложности.

### 11.1. Прямой маршрут без LLM

Для однозначных команд использовать заранее определённые обработчики, например:

- открыть Discord;
- проверить, запущен ли Discord;
- найти конкретный файл;
- удалить явно названный файл после подтверждения;
- показать статус Ollama.

Цель — минимальная задержка и отсутствие лишней нагрузки на Qwen.

### 11.2. Лёгкая модель

Для простых, но не полностью шаблонных фраз допускается отдельная небольшая модель.

### 11.3. Мощная модель

Qwen используется для:

- неоднозначных формулировок;
- многошаговых задач;
- задач с контекстом диалога;
- выбора между несколькими инструментами;
- подготовки параметров для сложного действия.

Роутер должен выбирать самый быстрый подходящий маршрут автоматически.

## 12. Интерфейс PySide6

Основные части:

- чат;
- настройки;
- инструменты;
- статистика генерации;
- управление Ollama;
- отображение текущего имени ассистента;
- индикаторы состояния сервера и модели.

Настройки должны сохраняться между запусками. Изменение переключателей инструментов должно влиять и на UI, и на серверную проверку в `ToolExecutor`.

## 13. Зависимости и запуск

На старте приложение должно проверять наличие:

- Python/runtime для режима исходников;
- PySide6;
- `requests`;
- `psutil`;
- остальных обязательных библиотек;
- нужных ресурсов и конфигурационных файлов.

Если зависимость отсутствует:

- показать понятное состояние;
- установить её автоматически, если это разрешено режимом запуска;
- не скачивать повторно уже установленное;
- сохранять версии и результат проверки.

Для будущего `.exe` Python runtime и основные зависимости должны поставляться вместе с приложением. Ollama первоначально остаётся отдельной установленной системой.

## 14. Сборка в `.exe`

Целевой пользовательский сценарий:

- пользователь запускает один `Jarvis.exe`;
- Python и основные библиотеки ему вручную не нужны;
- Ollama работает как отдельный локальный компонент;
- приложение умеет находить свой корень по расположению `.exe`;
- перенос на другой диск не ломает sandbox и настройки.

Рекомендуемая структура поставки:

```text
Jarvis/
├── Jarvis.exe
├── runtime/
├── resources/
├── logs/
└── workspace/
```

Пользовательские настройки и разрешения желательно хранить в `%APPDATA%\Jarvis\`.

## 15. Голосовой режим, следующий этап

Будущая цепочка:

```text
Микрофон → Whisper → текст → Command Router → инструмент/LLM → ответ
```

Требования:

- настраиваемое ключевое слово;
- значение по умолчанию — `Jarvis`;
- пользователь может заменить его, например на `Джелрик`;
- голосовой режим использует текущее значение из настроек, а не жёстко зашитую строку;
- должна быть настройка, реагировать ли только после ключевого слова или на каждую фразу;
- обычные разговоры в Discord не должны автоматически запускать команды без условий активации.

## 16. Логирование и диагностика

Нужны журналы для:

- запуска и остановки Ollama;
- выбора маршрута Command Router;
- вызовов инструментов;
- отклонённых путей;
- ошибок удаления и запуска;
- фактической проверки результата;
- времени генерации, токенов и скорости.

Секреты, токены и чувствительные данные не должны попадать в обычный лог.

## 17. Тестирование

Обязательные группы тестов:

### 17.1. Безопасность путей

- `../secret`;
- абсолютный путь на том же диске;
- путь на другом диске;
- символическая ссылка наружу;
- junction наружу;
- смешанные разделители;
- нестандартный регистр.

### 17.2. Файловые операции

- удаление существующего файла;
- удаление несуществующего файла;
- удаление занятого файла;
- удаление `.lnk` при запущенном целевом приложении;
- отсутствие ложного успеха;
- неоднозначное имя;
- точное расширение.

### 17.3. Естественные формулировки

- «удали ярлык Discord»;
- «удали Discord.exe»;
- «найди файл настроек»;
- «открой ярлык Prism Launcher»;
- варианты синонимов и разговорных фраз.

### 17.4. Ollama

- сервер уже запущен;
- сервер остановлен;
- двойной запуск;
- недоступный API;
- модель загружена/выгружена;
- корректное обновление статуса в UI.

## 19. Критерии готовности первой стабильной версии

Первая стабильная версия считается готовой, если:

- Jarvis работает после перемещения проекта на другой диск;
- файловые инструменты не выходят за пределы sandbox;
- пути с `..`, абсолютные пути и ссылки наружу блокируются;
- «ярлык» не подменяется `.exe`;
- удаление подтверждается фактическим отсутствием файла;
- ошибки удаления показываются как ошибки;
- имя ассистента обновляет заголовок окна;
- сервер Ollama запускается и останавливается кнопками;
- статус сервера и модели отображается раздельно;
- простые команды могут выполняться без Qwen;
- выключенный инструмент нельзя вызвать обходом UI;
- критические сценарии покрыты тестами.
