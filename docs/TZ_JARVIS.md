# Актуальное ТЗ проекта Jarvis

**Версия документа:** 2.0  
**Дата обновления:** 2026-09-12  
**Проект:** локальный голосовой/текстовый ассистент Jarvis для Windows 11  
**Стек:** Python, PySide6, Ollama, локальные LLM, в будущем Whisper  
**Репозиторий:** `jelr1k/localjarvisgolos`

> Документ содержит только оставшиеся задачи. Базовая архитектура, sandbox, управление путями, файловые инструменты, базовое управление Ollama, логирование, базовые тесты и прочие уже реализованные пункты исключены из текущего списка работ.

## 1. Следующий этап: полноценная маршрутизация команд

Сейчас в проекте уже существует базовый Command Router, но его необходимо полностью подключить к пользовательскому вводу.

### 1.1. Единая точка входа

Каждое сообщение из текущего чата должно проходить через Command Router до обращения к LLM.

Схема:

```text
Пользовательский ввод
        ↓
Command Router
        ├─ однозначная простая команда → прямой инструмент
        ├─ простая, но не шаблонная команда → малая модель
        └─ сложная/неоднозначная команда → основная модель
```

Пользователь не должен запускать Router вручную. Он является внутренним этапом обработки сообщения.

### 1.2. Простые команды без LLM

Команды, которые можно определить надёжно без языковой модели, должны выполняться напрямую.

Примеры:

- «Запусти Discord»;
- «Открой ярлык Discord»;
- «Проверь, запущен ли Discord»;
- «Найди файл test.txt»;
- «Удалить test.txt» после подтверждения;
- «Покажи статус Ollama».

Для таких команд вызов основной LLM не требуется.

### 1.3. Безопасность маршрутизации

Command Router не должен обходить существующие проверки инструментов.

Любой выбранный инструмент всё равно проходит через `ToolExecutor`, проверку разрешений, sandbox и фактическую проверку результата.

## 2. Маршрутизация между несколькими моделями

Необходимо реализовать полноценный выбор модели по сложности задачи.

### 2.1. Простые задачи

Для команд, которые требуют понимания естественного языка, но не требуют сложного рассуждения, допускается использование небольшой быстрой модели.

Пример:

```text
«Пожалуйста, открой Discord»
```

### 2.2. Сложные задачи

Для многошаговых и неоднозначных задач использовать основную мощную модель Qwen.

Пример:

```text
«Открой Discord, проверь, запущен ли он, и после этого найди в рабочей папке файл с настройками»
```

### 2.3. Выбор маршрута

Роутер должен учитывать:

- количество действий;
- наличие нескольких объектов;
- неоднозначность формулировки;
- необходимость контекста диалога;
- необходимость вызова нескольких инструментов;
- наличие подходящего прямого обработчика.

Путь обработки должен выбираться автоматически.

## 3. Полная интеграция Tool Calling с чатом

Необходимо довести текущую интеграцию инструментов до законченного пользовательского поведения.

Требуется обеспечить цикл:

```text
сообщение
  ↓
Router
  ↓
LLM (если нужна)
  ↓
tool call
  ↓
ToolExecutor
  ↓
результат
  ↓
LLM/Router при необходимости продолжает задачу
  ↓
финальный ответ пользователю
```

При этом пользователь должен видеть нормальный итог выполнения, а не внутренние JSON-структуры инструментов.

## 4. Голосовое управление

### 4.1. Распознавание речи

Добавить Whisper или совместимое локальное решение для преобразования речи в текст.

Цепочка:

```text
Микрофон
   ↓
Whisper
   ↓
текст
   ↓
Command Router
   ↓
инструмент / малая модель / Qwen
```

Распознавание должно выполняться локально.

### 4.2. Wake word

Добавить настраиваемое ключевое слово.

По умолчанию:

```text
Jarvis
```

Пользователь должен иметь возможность изменить его, например на:

```text
Джелрик
```

Ключевое слово хранится в настройках и не должно быть жёстко зашито в код.

### 4.3. Режим активации

Добавить настройку режима:

- реагировать только после wake word;
- обрабатывать каждую распознанную фразу.

По умолчанию безопаснее использовать режим с wake word.

### 4.4. Защита от случайной активации

Обычный разговор, звук Discord и другие фоновые фразы не должны автоматически превращаться в команды без выполнения условий активации.

## 5. Голосовой ответ

Добавить локальный синтез речи после текстового ответа Jarvis.

Цепочка:

```text
команда
  ↓
обработка
  ↓
текстовый ответ
  ↓
TTS
  ↓
голос Jarvis
```

Должны быть настройки:

- включение/выключение голосового ответа;
- выбор голоса;
- скорость речи;
- громкость.

## 6. Настройки голоса и юмористических ответов

В голосовом режиме предусмотреть настраиваемую вероятность случайной юмористической реплики при выполнении команды.

Например, Jarvis обычно отвечает нормально, но с небольшой заданной вероятностью может произнести пафосную или абсурдную мемную фразу.

Требования:

- вероятность регулируется пользователем;
- значение `0%` полностью отключает эффект;
- эффект не должен мешать выполнению команды;
- юмористическая фраза не должна заменять сообщение об ошибке;
- фразы должны генерироваться/выбираться так, чтобы не нарушать обычную логику ассистента.

## 7. Полноценная упаковка в `.exe`

Необходимо подготовить конечную пользовательскую сборку.

### 7.1. Запуск

Итоговый сценарий:

```text
Jarvis.exe
   ↓
GUI запускается без ручного CMD
```

Пользователю не требуется вручную запускать Python-файл.

### 7.2. Переносимость

Сборка должна сохранять уже реализованное поведение автоматического определения своего корня.

После переноса:

```text
C:\Jarvis
```

в:

```text
D:\Apps\Jarvis
```

приложение должно продолжать работать без изменения путей в исходниках или конфигурации.

### 7.3. Режим поставки

Python runtime и основные Python-зависимости должны входить в сборку.

Ollama остаётся отдельной локальной зависимостью, если выбранная конечная архитектура не предусматривает её встраивание.

## 8. Проверка сборки на реальном Windows

После реализации `.exe` обязательно проверить на Windows 11:

- запуск на чистой директории;
- запуск после переноса на другой диск;
- автоматическое создание необходимых директорий;
- создание/загрузка пользовательских настроек;
- работу sandbox;
- работу файловых инструментов;
- запуск и состояние Ollama;
- загрузку и выгрузку модели;
- работу Command Router;
- отсутствие зависания GUI;
- корректное завершение приложения.

## 9. Финальная приёмка текущего этапа

Этап считается завершённым, когда:

- любое сообщение чата автоматически проходит через Command Router;
- простые команды выполняются напрямую без основной LLM;
- сложные команды корректно передаются нужной модели;
- цепочка tool calling полностью работает от ввода до финального ответа;
- голосовой ввод распознаётся локально;
- wake word настраивается пользователем;
- обычный фоновый разговор не вызывает команды без условий активации;
- голосовые ответы работают локально и имеют настройки;
- юмористические реплики имеют регулируемую вероятность;
- приложение собирается в рабочий `.exe`;
- `.exe` корректно работает после переноса на другой диск;
- весь основной пользовательский сценарий проверен на Windows 11.

## 10. Что не нужно повторно реализовывать

Следующие компоненты уже являются частью текущей кодовой базы и не должны рассматриваться как новые задачи при дальнейшем развитии:

- автоматическое определение корня Jarvis;
- автоматическое создание рабочих директорий;
- переносимость между дисками;
- хранение пользовательских настроек независимо от директории установки;
- sandbox и базовый слой безопасности;
- валидация безопасных путей;
- базовый `ToolExecutor`;
- базовые файловые инструменты;
- базовые инструменты приложений;
- проверка фактического результата файловых операций;
- базовая обработка ярлыков и неоднозначных совпадений;
- управление сервером Ollama из UI;
- загрузка и выгрузка модели;
- раздельное отображение состояния сервера и модели;
- синхронизация имени ассистента с окном;
- буферизация потокового вывода;
- фоновые задачи мониторинга;
- логирование;
- базовые тесты и CI-инфраструктура.
