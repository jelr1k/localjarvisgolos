# Актуальное ТЗ проекта Jarvis

**Версия документа:** 2.3  
**Дата обновления:** 2026-09-16  
**Проект:** локальный голосовой/текстовый ассистент Jarvis для Windows 11  
**Стек:** Python, PySide6, Ollama, локальные LLM, faster-whisper  
**Репозиторий:** `jelr1k/localjarvisgolos`  
**Основная ветка текущей разработки:** `osnova`

> Документ отражает фактическое состояние кода `osnova` и требования, которые ещё не реализованы.

## 0. Текущее состояние

### 0.1. Архитектура — ГОТОВО

Реализованы:

- автоматическое определение корня Jarvis;
- рабочий `Workspace` относительно расположения приложения;
- пользовательские настройки и алиасы;
- sandbox и безопасная работа с путями;
- файловые инструменты;
- инструменты управления приложениями и Windows-ярлыками;
- Command Router;
- ограниченный tool scope для конкретного запроса;
- многораундовый Tool Calling;
- управление Ollama Server и моделью из UI;
- расширенное логирование;
- тесты ключевых компонентов.

### 0.2. Command Router — ГОТОВО

```text
Пользовательский ввод
        ↓
Command Router
        ├─ простая однозначная команда → прямой инструмент
        └─ сложная/составная задача → LLM + разрешённые tools
```

Обычный разговор не должен получать полный набор системных и файловых инструментов.

### 0.3. Tool Calling — ГОТОВО

`GenerationWorker` поддерживает до 5 последовательных раундов Tool Calling. После каждого вызова результат возвращается модели для продолжения задачи или формирования финального ответа.

### 0.4. Файловая подсистема — РЕАЛИЗОВАНА, НО ЕСТЬ БАГ

Поиск и чтение файлов реализованы внутри разрешённого `Workspace`. Поддерживается неоднозначность, когда существует несколько реальных совпадений.

Однако подтверждён баг с разрешением имён файлов после голосового ввода и между разными файловыми командами. Подробности находятся в `docs/BUG_VOICE_FILE_NAME_RESOLUTION.md`.

Требование: все команды открытия, поиска и чтения должны использовать единый resolver и проверять фактическое содержимое `Workspace`.

### 0.5. Голосовой ввод — ЧАСТИЧНО ГОТОВО

Локальный STT реализован через `faster-whisper`.

Текущая реализация `voice/speech_recognizer.py` использует:

- модель `small`;
- `device="cpu"`;
- `compute_type="int8"`;
- язык `ru`;
- целевую частоту 16 kHz;
- `beam_size=5`;
- `vad_filter=True`;
- ленивую загрузку модели;
- ресэмплинг входного аудио к 16 kHz при необходимости.

Распознанный текст передаётся в существующий путь обработки сообщений и далее в Command Router/LLM. Whisper не должен самостоятельно решать, существует ли файл.

### 0.6. Требование к STT и именам файлов

Ошибки распознавания являются ожидаемой особенностью STT и не должны ломать файловую систему.

Например:

```text
«тест точка txt»
        ↓
STT может получить разные варианты текста
        ↓
resolver проверяет реальные объекты Workspace
        ↓
test.txt найден, если он реально существует
```

Нельзя объявлять `test.exe` существующим только потому, что Whisper так распознал слово. Нельзя выдавать вымышленные кандидаты.

## 1. Следующие задачи

### 1.1. Исправление разрешения имён файлов — В РАБОТЕ

Необходимо:

- унифицировать поиск файлов для открытия, чтения и других файловых команд;
- использовать фактическое содержимое `Workspace` как источник истины;
- добавить нормализацию имён и расширений после STT;
- поддержать контролируемое сопоставление с реальными файлами при небольших ошибках распознавания;
- при нескольких реальных совпадениях показывать список и принимать номер выбора;
- не создавать ложные кандидаты.

### 1.2. Обновление интерфейса загрузки файлов в Workspace — ПЛАН

Необходимо обновить пользовательский интерфейс добавления файлов в `Workspace`, чтобы загрузка была понятной и удобной без ручного перемещения файлов через Проводник.

Целевое поведение:

- добавление одного или нескольких файлов через стандартный выбор файлов;
- поддержка добавления файлов в `Workspace` через drag-and-drop, если это возможно для текущего UI;
- понятное отображение выбранных файлов перед добавлением;
- отображение состояния операции: ожидание, копирование, успешно добавлено, ошибка;
- явное отображение итогового расположения файла внутри `Workspace`;
- корректная обработка конфликтов имён без перезаписи файлов без явного решения пользователя;
- соблюдение sandbox: интерфейс загрузки не должен позволять записывать объект за пределы `Workspace`;
- после успешного добавления файл должен сразу становиться доступным файловым инструментам и единому resolver.

### 1.3. Wake word — ПЛАН

По умолчанию: `Jarvis`.

### 1.4. Полноценный голосовой режим — ПЛАН

Нужно добавить постоянное ожидание/активацию по wake word без превращения фоновой речи, игр и Discord в команды.

### 1.5. TTS — ПЛАН

Добавить локальный синтез речи с настройками голоса, скорости, громкости и включения/выключения.

### 1.6. Финальная сборка `.exe` — ПЛАН

Проверить запуск без ручного CMD, переносимость между дисками, sandbox, Ollama, файловые и системные инструменты, голосовой режим и корректное завершение приложения.

## 2. Планы на будущее

### 2.1. Model Router — ПЛАН НА БУДУЩЕЕ

Отдельный слой автоматического выбора модели по типу и сложности задачи пока не реализован и не относится к текущему этапу разработки.

В будущем Model Router должен автоматически выбирать подходящую локальную модель с учётом типа задачи, требуемого качества, доступных ресурсов и характеристик компьютера.

### 2.2. Другие перспективные направления

К дальнейшему развитию относятся функции, которые не являются частью ближайшего этапа стабилизации:

- расширение доступа за пределы `Workspace` через Permission System;
- долгосрочная память;
- модульная архитектура специализированных функций;
- браузерная автоматизация;
- дополнительные голосовые возможности;
- расширенное управление процессами;
- дополнительные способы автоматизации.

## 3. Сетевая особенность голосовой подсистемы

В пользовательском окружении локальный Happ может предоставлять прокси `127.0.0.1:10808`. Python/Hugging Face иногда получает этот адрес как SOCKS4-прокси и выдаёт `Unknown scheme for proxy URL`.

Это относится к сетевому окружению, а не к модели Whisper. При необходимости запуск Jarvis должен иметь возможность работать без наследования внешнего proxy для прямых сетевых операций.

## 4. Критерии готовности голосового ввода

Голосовой ввод считается полностью готовым для файловых команд, когда:

- Whisper стабильно преобразует аудио в текст;
- ошибки STT не приводят к ложному существованию файлов;
- реальный `test.txt` находится одинаково при открытии и чтении;
- поиск кандидатов идёт только по фактическому `Workspace`;
- неоднозначность разрешается через выбор пользователя;
- распознанный текст проходит через существующий Command Router;
- обычный разговор не вызывает файловые tools без соответствующего намерения.
