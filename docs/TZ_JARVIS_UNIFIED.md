# Jarvis — единое ТЗ проекта

**Версия документа:** 1.1  
**Дата обновления:** 2026-09-16  
**Проект:** локальный голосовой/текстовый ассистент Jarvis для Windows 11  
**Стек текущей реализации:** Python, PySide6, Ollama, локальные LLM, faster-whisper  
**Репозиторий:** `jelr1k/localjarvisgolos`  
**Основная ветка текущей разработки:** `osnova`

> **Назначение документа:** единое ТЗ, объединяющее фактическое состояние текущей реализации Jarvis и целевое направление развития проекта.
>
> Документ разделяет уже реализованные возможности, задачи текущего этапа и перспективные требования. Перспективные требования не считаются реализованными только потому, что описаны здесь.

---

## 0. Общая концепция

Jarvis должен развиваться из локального голосового/текстового помощника и лаунчера в полноценного локального AI-оператора компьютера.

Основная идея: пользователь формулирует задачу обычным языком или голосом, после чего Jarvis определяет необходимое действие, проверяет разрешения и выполняет его с минимально необходимым использованием ресурсов.

Jarvis является прежде всего локальным приложением для управления ПК. Настройки, история, память, разрешения и другие пользовательские данные по возможности должны оставаться локально на компьютере.

### Основные принципы

- локальная работа;
- минимальное потребление CPU, RAM и VRAM;
- управление естественным языком и голосом;
- детерминированные действия без LLM там, где LLM не нужна;
- Command Router как первый уровень обработки команды;
- отдельная система разрешений, не зависящая от решения LLM;
- широкая настройка через UI;
- модульность;
- расширение доступа к компьютеру только вместе с системой доверия и разрешений;
- отсутствие необходимости редактировать исходный код или JSON для обычной настройки;
- возможность расширять функциональность без переписывания ядра.

# 1. Архитектура и текущий статус

## 1.1. Текущая архитектура — ГОТОВО

В ветке `osnova` реализованы базовые архитектурные компоненты:

- автоматическое определение корня Jarvis;
- `Workspace`, определяемый относительно расположения приложения;
- пользовательские настройки и алиасы;
- sandbox и безопасная работа с путями;
- файловые инструменты;
- инструменты управления приложениями и Windows-ярлыками;
- Command Router;
- ограниченный tool scope для конкретного запроса;
- многораундовый Tool Calling;
- управление Ollama Server и моделью из UI;
- расширенное логирование;
- тесты ключевых компонентов.

## 1.2. Command Router — ГОТОВО

Базовая схема:

```text
Пользовательский ввод
        ↓
Command Router
        ├─ простая однозначная команда → прямой инструмент
        └─ сложная/составная задача → LLM + разрешённые tools
```

Обычный разговор не должен получать полный набор системных и файловых инструментов.

Простые детерминированные команды не должны загружать LLM.

Примеры:

- открыть приложение;
- закрыть приложение;
- открыть папку;
- создать файл;
- запустить профиль;
- открыть сайт.

LLM используется там, где действительно требуется понимание естественного языка, планирование или обработка сложного контекста.

## 1.3. Tool Calling — ГОТОВО

`GenerationWorker` поддерживает до 5 последовательных раундов Tool Calling. После каждого вызова результат возвращается модели для продолжения задачи или формирования финального ответа.

LLM не должна самостоятельно выполнять системные действия вне разрешённого набора инструментов.

# 2. Workspace, доступ к ПК и безопасность

## 2.1. Текущий Workspace

На текущем этапе `Workspace` является границей безопасной работы Jarvis.

Все файловые операции и запуск объектов по умолчанию должны выполняться внутри автоматически определяемого Workspace. Путь Workspace должен оставаться переносимым при перемещении Jarvis между дисками.

## 2.2. Будущее расширение доступа

Workspace является текущей защитной моделью разработки, но не обязательно конечным ограничением Jarvis.

В перспективе Jarvis должен уметь работать с объектами всего компьютера, однако расширение доступа должно сопровождаться отдельной системой разрешений и доверия.

Пример целевого поведения:

```text
Пользователь
    ↓
Router
    ↓
Permission System
    ↓
разрешено / подтверждение / запрещено
    ↓
Выполнение / подтверждение / отказ
```

Полный доступ к ПК не должен означать безусловное выполнение любых действий.

## 2.3. Система разрешений — ПЛАН

Система разрешений должна быть независимой от LLM.

Предполагаемые уровни:

- безопасные действия — выполняются автоматически;
- потенциально опасные — требуют подтверждения;
- критические — требуют повышенного подтверждения или могут быть запрещены полностью.

Пользователь должен иметь возможность задавать доверенные папки.

Системные и критические области Windows должны иметь более строгие ограничения.

LLM не должна самостоятельно определять собственные права.

# 3. Работа с файлами

## 3.1. Текущее состояние

Файловая подсистема реализована внутри разрешённого Workspace.

Поддерживается неоднозначность, когда существует несколько реальных совпадений.

Однако подтверждён баг с разрешением имён файлов после голосового ввода и между разными файловыми командами. Подробности находятся в `docs/BUG_VOICE_FILE_NAME_RESOLUTION.md`.

## 3.2. Единый resolver — В РАБОТЕ

Необходимо:

- унифицировать поиск файлов для открытия, чтения и других файловых команд;
- использовать фактическое содержимое Workspace как источник истины;
- добавить нормализацию имён и расширений после STT;
- поддержать контролируемое сопоставление с реальными файлами при небольших ошибках распознавания;
- при нескольких реальных совпадениях показывать список и принимать номер выбора;
- не создавать ложные кандидаты.

Whisper/STT не должен самостоятельно решать, существует ли файл.

Например:

```text
«тест точка txt»
        ↓
STT получает текст
        ↓
единый resolver
        ↓
проверка реальных объектов Workspace
        ↓
test.txt найден, если он действительно существует
```

Нельзя объявлять `test.exe` существующим только потому, что STT так распознал слово.

## 3.3. Целевые файловые возможности

В перспективе Jarvis должен поддерживать:

- поиск;
- чтение;
- анализ;
- создание;
- открытие;
- редактирование;
- переименование;
- перемещение;
- удаление;
- запись указанного пользователем текста;
- генерацию текста и сохранение результата в файл;
- поиск по содержимому;
- работу с папками.

Поддерживаемые пользовательские объекты должны включать, где технически применимо:

- `.exe`;
- `.lnk`;
- `.url`;
- `.txt`;
- `.bat`;
- `.cmd`;
- `.json`;
- `.py`;
- `.ini`;
- `.cfg`;
- другие обычные пользовательские файлы.

Пользователь не должен быть обязан знать расширение объекта. Например, команда `запусти Steam` должна находить подходящий ярлык или исполняемый объект самостоятельно.

Полноценное интеллектуальное редактирование больших программных проектов не является первоочередной задачей. Базовое создание и изменение текстовых файлов должно появиться раньше.

## 3.4. Интерфейс загрузки файлов в Workspace — ПЛАН

Jarvis должен получить обновлённый UI для добавления файлов в `Workspace`, чтобы пользователь мог переносить файлы в рабочую область непосредственно из приложения.

Целевое поведение:

- выбор одного или нескольких файлов через стандартный диалог;
- drag-and-drop файлов в интерфейс, если это поддерживается текущим UI;
- предварительный список выбранных файлов;
- отображение состояния операции: ожидание, копирование, успешно добавлено, ошибка;
- отображение итогового пути внутри `Workspace`;
- обработка конфликтов имён без автоматической перезаписи без явного решения пользователя;
- запрет записи за пределы `Workspace`;
- немедленная доступность успешно добавленных файлов для файловых инструментов и единого resolver;
- возможность дальнейшего расширения UI для работы с алиасами добавленного объекта.

Интерфейс загрузки не должен обходить sandbox и не должен создавать отдельный путь работы с файлами, не связанный с общей файловой подсистемой.

# 4. Запуск приложений, игр и процессов

## 4.1. Запуск

Jarvis должен уметь запускать пользовательские приложения, игры и другие объекты Windows.

Целевой принцип: если Windows умеет запустить пользовательский объект, Jarvis должен по возможности уметь запустить его через соответствующий инструмент.

Должны поддерживаться `.exe`, `.lnk`, `.url`, `.bat`, `.cmd` и другие подходящие объекты.

Пользователь должен иметь возможность обращаться к объекту по понятному имени или алиасу без обязательного указания расширения.

## 4.2. Закрытие

Jarvis должен уметь:

- находить связанные с приложением процессы;
- корректно закрывать приложение;
- при необходимости завершать процесс, если это разрешено;
- работать с приложениями независимо от способа их запуска;
- избегать завершения несвязанных системных процессов.

В перспективе определение процесса не должно основываться только на имени `.exe`.

Следует учитывать:

- имя процесса;
- путь к исполняемому файлу;
- родительский процесс;
- издателя / цифровую подпись, если доступна;
- связь процесса с конкретным приложением;
- пользовательский или системный контекст;
- другие признаки, позволяющие отличить нужное приложение от системного процесса.

Если Jarvis не уверен, какой процесс является нужным, он должен показать найденную информацию и запросить подтверждение.

## 4.3. Системные процессы

Системные и критические процессы должны быть защищены от случайного завершения.

---

# 5. Выполнение CMD и PowerShell

Jarvis должен в перспективе уметь выполнять команды через Windows CMD, PowerShell и другие подходящие системные интерфейсы.

LLM может помогать интерпретировать сложный запрос, но фактическое выполнение должно проходить через Command Router, разрешённые инструменты и Permission System.

LLM не должна самостоятельно придумывать опасные действия и выполнять их только потому, что они логически следуют из рассуждения.

Например, запрос не должен автоматически превращаться в произвольную команду удаления системных файлов без отдельной проверки разрешений.

# 6. Голосовая подсистема

## 6.1. Текущая реализация STT — ЧАСТИЧНО ГОТОВО

Локальный STT реализован через `faster-whisper`.

Текущая реализация `voice/speech_recognizer.py` использует:

- модель `small`;
- `device="cpu"`;
- `compute_type="int8"`;
- язык `ru`;
- целевую частоту 16 kHz;
- `beam_size=5`;
- `vad_filter=True`;
- ленивую загрузку модели;
- ресэмплинг входного аудио к 16 kHz при необходимости.

Распознанный текст передаётся в существующий путь обработки сообщений и далее в Command Router/LLM.

## 6.2. Требования к STT

Ошибки распознавания не должны ломать файловую систему и не должны создавать вымышленные объекты.

Распознанный текст должен проходить через обычный Command Router, а не обходить его.

## 6.3. Независимость STT — ПЛАН

Архитектура голосового слоя не должна быть жёстко привязана к `faster-whisper`. Он является текущей реализацией и должен при необходимости заменяться другим локальным STT.

## 6.4. Wake word — ПЛАН

Wake word должно настраиваться пользователем.

Значение по умолчанию: `Jarvis`.

Фоновая речь, игры и обычные разговоры не должны случайно превращаться в команды.

## 6.5. Полноценный голосовой режим — ПЛАН

Целевые возможности:

- запуск приложений;
- открытие файлов и папок;
- создание и изменение файлов;
- удаление объектов с подтверждением;
- закрытие приложений;
- поиск файлов;
- выполнение команд;
- запуск профилей;
- обычный диалог;
- выполнение сложных задач.

## 6.6. Голосовое подтверждение — ПЛАН

Для опасных действий должна быть возможность голосового подтверждения.

Подтверждение должно быть связано с конкретным ожидающим действием. Обычное слово `да`, сказанное позже в другом разговоре, не должно подтверждать старую операцию.

## 6.7. TTS — ПЛАН

Добавить локальный синтез речи с настройками:

- включение/выключение;
- голос;
- скорость;
- громкость;
- другие параметры, доступные выбранному движку.

# 7. Управление жизненным циклом LLM

LLM должна загружаться только при необходимости.

Простые команды, обработанные напрямую Router, не должны запускать LLM.

После настраиваемого периода бездействия модель должна выгружаться из памяти. Ориентир: 3–5 минут, но значение должно задаваться пользователем.

Цели:

- не занимать VRAM/RAM без необходимости;
- не снижать FPS во время игр;
- не держать тяжёлые процессы постоянно активными;
- сохранять возможность быстро использовать LLM при необходимости.

Jarvis должен показывать пользователю состояние LLM и связанных компонентов.

---

# 8. Ollama и локальные компоненты

Jarvis должен уметь определять наличие необходимых локальных компонентов, включая:

- Ollama или другой локальный LLM runtime;
- локальную модель;
- Whisper / faster-whisper;
- дополнительные библиотеки;
- специализированные модули.

## 8.1. Первый запуск

При первом запуске Jarvis должен определить:

- какие компоненты установлены;
- какие отсутствуют;
- какие функции из-за этого недоступны;
- совместимы ли компоненты с текущей системой.

Если автоматическая установка возможна, Jarvis должен предлагать или выполнять её через понятный UI.

Если автоматическая установка невозможна, приложение должно показывать ясные инструкции.

После установки желательно автоматически проверить работоспособность компонента и зарегистрировать его состояние.

Компоненты по возможности должны управляться из самого приложения.

## 8.2. Управление Ollama — ТЕКУЩАЯ ФУНКЦИЯ

В текущей архитектуре предусмотрено управление Ollama Server и моделью из UI.

В дальнейшем интерфейс должен позволять пользователю видеть состояние runtime и модели, а также выполнять необходимые действия запуска/остановки без ручного CMD.

---

# 9. Определение возможностей компьютера

Jarvis должен уметь оценивать характеристики системы перед выбором тяжёлых компонентов:

- CPU;
- GPU;
- объём VRAM;
- RAM;
- свободное место на диске;
- версия Windows;
- версия Python и другие необходимые параметры;
- доступность аппаратного ускорения;
- другие характеристики, влияющие на производительность.

На основании этих данных Jarvis может рекомендовать подходящие модели и настройки.

Рекомендация не должна автоматически превращаться в принудительный выбор.

---

# 10. Память и контекст — ПЛАН

Jarvis должен иметь долгосрочную память, но пользователь должен полностью контролировать её использование.

Потенциально сохраняемые данные:

- прошлые диалоги;
- предпочтения пользователя;
- выполненные задачи;
- контекст проектов и файлов;
- настройки;
- полезная информация из прошлой работы.

## 10.1. Управление памятью

UI должен позволять:

- включать и отключать память;
- выбирать, что запоминать;
- выбирать, какие данные использовать в новом контексте;
- удалять отдельные воспоминания;
- удалять диалоги;
- запрещать использование старых диалогов;
- задавать поведение контекста.

Пользователь должен иметь возможность запретить использование конкретного старого диалога как контекста.

Память должна храниться локально и не отправляться разработчикам или сторонним серверам без явного основания и разрешения пользователя.

---

# 11. Фоновая работа и Windows

## 11.1. Фоновый режим — ПЛАН

Jarvis должен быть обычным фоновой Windows-приложением с возможностью:

- автоматического запуска вместе с Windows;
- работы в фоне;
- наличия значка в системном трее;
- отключения автозапуска;
- полного выхода через трей.

Лёгкий голосовой компонент может работать в фоне, при этом LLM не обязана быть загружена.

- Settings;

- Tools;
- Voice;
- Permissions;
- Modules;
- Profiles;
- Logs / Diagnostics;
- System State.

Интерфейс загрузки файлов в `Workspace` должен быть частью общей UI-системы, а не отдельным обходным механизмом.

Точная структура UI может изменяться.

---

# 13. Модульная архитектура — ПЛАН

Ядро должно содержать базовые системы:

- UI;
- Command Router;
- Permission System;
- голосовой слой;
- интеграцию с LLM;
- память;
- базовые инструменты;
- управление состоянием приложения.

Специализированные функции должны по возможности быть отдельными модулями.

Примеры:

- Minecraft;
- управление браузером;
- скриншоты;
- интеграции с конкретными приложениями;
- другие специализированные функции.

Пользователь должен иметь возможность:

- включать и отключать модуль;
- видеть требования модуля;
- устанавливать модуль через UI;
- устанавливать необходимые библиотеки, если это технически возможно;
- регистрировать модуль в Router.

Точная plugin-архитектура пока не фиксируется.

---

# 14. Профили и сценарии — ПЛАН

Jarvis должен поддерживать пользовательские профили, представляющие собой сохранённые последовательности детерминированных действий.

Пример игрового профиля:

```text
Закрыть Telegram
Открыть Steam
Открыть Minecraft Launcher
Открыть Discord
```

Пользователь может сказать `Запусти игровой профиль`, после чего Jarvis выполняет сохранённую последовательность без загрузки LLM.

Профили должны:

- создаваться пользователем;
- редактироваться через UI;
- храниться локально;
- работать без постоянно загруженной LLM.

Условные автоматизации вида `если X произошло → выполнить Y` являются дальнейшим расширением, а не обязательной частью первой версии профилей.

# 15. Браузер и интернет — ПЛАН

Jarvis должен уметь взаимодействовать с браузером, если это можно реализовать без неприемлемого расхода ресурсов.

Целевые сценарии:

- открыть Discord;
- открыть VK;
- открыть произвольный сайт;
- открыть конкретный URL;
- выполнить поиск в интернете;
- найти документацию;
- найти видео;
- открыть результаты поиска;
- работать с конкретным сайтом.

Более сложная browser automation может быть добавлена позже.

Если использование локальной LLM делает браузерную автоматизацию непрактично медленной, приоритет остаётся за производительностью и полезностью.

Браузерные действия должны проходить через общую систему разрешений.

# 16. Локальные данные и сеть

По умолчанию локально должны оставаться:

- настройки;
- память;

- конфигурация;
- разрешения;
- профили;
- алиасы;

Интернет должен использоваться только там, где это необходимо, например для:

Собственный обязательный удалённый сервер для основной работы Jarvis не является целью.

# 17. Логи и диагностика

Логирование должно использоваться для диагностики ключевых компонентов Jarvis.

Необходимо сохранять достаточно информации для расследования ошибок, в том числе проблем:

- Command Router;
- Tool Calling;
- файлового resolver;
- STT;
- запуска и закрытия приложений;
- процессов;
- Ollama;
- LLM;
- модулей;
- системных инструментов.

При этом секреты, пароли, токены и иные чувствительные данные не должны записываться в лог без необходимости.

UI должен предоставлять доступ к диагностике и логам.

---

# 18. Сетевая особенность голосовой подсистемы

В пользовательском окружении локальный Happ может предоставлять прокси `127.0.0.1:10808`. Python/Hugging Face иногда получает этот адрес как SOCKS4-прокси и выдаёт `Unknown scheme for proxy URL`.

Это относится к сетевому окружению, а не к модели Whisper.

При необходимости запуск Jarvis должен иметь возможность работать без наследования внешнего proxy для прямых сетевых операций.

---

# 19. Производительность и совместимость

Jarvis должен ориентироваться на работу на текущем компьютере пользователя и сопоставимом недорогом/среднем по мощности оборудовании.

Главные требования:

- не держать тяжёлые компоненты активными без необходимости;
- не загружать LLM для простых команд;
- минимизировать использование VRAM и RAM;
- учитывать производительность CPU/GPU;
- иметь возможность отключать тяжёлые функции;
- сохранять расширяемость для более мощных компьютеров.

Если функция технически возможна, но слишком тяжёлая для целевого оборудования, предпочтительно сделать её опциональной или отложить, а не заставлять весь Jarvis постоянно платить за неё ресурсами.

# 21. Критерии готовности текущей голосовой подсистемы

Голосовой ввод считается полностью готовым для файловых команд, когда:

- Whisper стабильно преобразует аудио в текст;
- ошибки STT не приводят к ложному существованию файлов;
- реальный `test.txt` находится одинаково при открытии и чтении;
- поиск кандидатов идёт только по фактическому Workspace;
- неоднозначность разрешается через выбор пользователя;
- распознанный текст проходит через существующий Command Router;
- обычный разговор не вызывает файловые tools без соответствующего намерения.

# 22. Критерии долгосрочной готовности Jarvis

Целевое состояние проекта достигается, когда Jarvis способен:

- принимать текстовые и голосовые команды;
- определять простые и сложные задачи через Router;
- выполнять простые действия без LLM;
- использовать LLM только там, где она действительно нужна;
- безопасно выполнять разрешённые действия;
- работать с файлами и приложениями;
- управлять процессами с защитой системных объектов;
- работать с ПК за пределами Workspace через Permission System;
- управлять локальной LLM и связанными компонентами;
- работать в фоне без постоянной загрузки LLM;
- поддерживать пользовательские профили, память и модули;
- предоставлять понятный UI для основных настроек;
- сохранять пользовательские данные локально по умолчанию;
- оставаться пригодным для работы на целевом оборудовании без бессмысленного расходования ресурсов.

# 24. Планы на будущее

## 24.1. Model Router — ПЛАН НА БУДУЩЕЕ

Отдельный слой автоматического выбора модели по типу и сложности задачи пока не реализован.

В будущем Model Router должен автоматически выбирать наиболее подходящую локальную модель с учётом:

- типа задачи;
- сложности запроса;
- требуемого качества;
- доступных CPU, RAM и VRAM;
- времени ответа;
- установленных моделей;
- текущей нагрузки системы.

Model Router должен оставаться отдельным уровнем архитектуры и не должен ломать базовый принцип Command Router: простые детерминированные команды не должны запускать LLM.
