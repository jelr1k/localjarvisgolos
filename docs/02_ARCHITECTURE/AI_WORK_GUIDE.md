# Руководство для ИИ по работе над Jarvis

**Назначение:** этот документ переносит рабочий контекст проекта в сам репозиторий, чтобы новый ИИ мог продолжить разработку без доступа к предыдущим личным чатам.

**Проект:** Jarvis — локальный текстовый/голосовой ассистент для Windows 11  
**Репозиторий:** `jelr1k/localjarvisgolos`  
**Актуальная рабочая ветка:** `osnova`

---

## 1. Главная идея документа

Репозиторий является главным источником технической правды. Этот документ описывает правила работы ИИ и актуальное состояние основных механизмов.

Не нужно пытаться восстановить старую переписку. Нужно восстановить состояние проекта по коду, тестам, документации, Git-истории и текущей задаче пользователя.

---

## 2. Порядок изучения проекта перед изменениями

Перед существенными изменениями пройти следующие этапы:

```text
1. Текущая ветка
        ↓
2. README.md
        ↓
3. docs/AI_WORK_GUIDE.md
        ↓
4. docs/TZ_JARVIS.md
        ↓
5. Структура каталогов
        ↓
6. Связанные исходные файлы
        ↓
7. Тесты
        ↓
8. Git diff / последние коммиты при необходимости
        ↓
9. Только после этого изменение кода
```

Если задача касается конкретной системы, сначала изучить реальную текущую реализацию, а не писать новую архитектуру поверх предположений.

Примеры:

- Ollama → `core/ollama_manager.py` и связанные классы;
- приложения/процессы → `tools/applications.py`, `tools/application_closer.py`;
- файлы/пути → `tools/`, `security/`;
- маршрутизация → `services/command_router.py`, `services/chat_service.py`;
- интерфейс → `ui/`;
- голос → `voice/`;
- настройки → `core/config_manager.py`, `config/`;
- алиасы → `core/alias_manager.py`.

## 3. Иерархия источников истины

Если информация конфликтует, использовать следующий приоритет:

1. **Фактический код текущей ветки.**
2. **Тесты**, если они проверяют соответствующее поведение.
3. `docs/AI_WORK_GUIDE.md`.
4. `docs/TZ_JARVIS.md`.
5. `README.md`.
6. Старые коммиты, комментарии и исторические документы.
7. Предположения ИИ.

Документация может устареть. Если код отличается от документации, сначала определить фактическое поведение и только затем решать, требуется ли изменение документации или кода.

## 4. Архитектура Jarvis

Jarvis — локальное настольное приложение под Windows 11 на Python/PySide6 с Ollama и локальной LLM.

Основной контур:

```text
Пользователь
    ↓
UI / голосовой ввод
    ↓
Command Router
    ├── однозначная простая команда → прямой Tool
    └── сложная/составная команда → LLM
                                      ↓
                                 Tool Calling
                                      ↓
                                 ToolExecutor
                                      ↓
                              permissions / sandbox
                                      ↓
                                реальное действие
                                      ↓
                              результат → ответ
```

Command Router не должен отправлять простую однозначную команду в LLM, если её можно безопасно выполнить напрямую.

Составные команды с несколькими действиями передаются в LLM для последовательного Tool Calling. `GenerationWorker` поддерживает до 5 последовательных раундов Tool Calling.

- пользовательские настройки через `ConfigManager`;
- Workspace;
- sandbox файловых операций;
- единый `ToolExecutor`;

- файловые инструменты;
- поиск и запуск приложений/файлов;
- проверка состояния процессов;
- закрытие приложений и деревьев процессов;
- алиасы;
- управление Ollama Server и моделями;

## 6. Принцип минимального изменения

При исправлении или добавлении функции менять минимально необходимое количество файлов.

Не следует без необходимости:

- переписывать большие файлы целиком;
- менять архитектуру ради небольшой функции;
- переименовывать десятки классов;
- удалять рабочую логику ради «более красивого» варианта;
- смешивать несколько независимых задач;
- менять формат конфигурации без миграции.

Если архитектурное изменение необходимо, сначала определить его причину, затронутые компоненты, возможные регрессии и способ проверки.

## 7. Безопасность файлов и системных действий

Файловые инструменты работают через существующий sandbox. Произвольное выполнение `cmd.exe`, PowerShell или `shell=True` не должно использоваться для обычных пользовательских операций, если существует безопасный инструмент.

Любой новый инструмент должен проходить через существующие разрешения и `ToolExecutor`, а не выполнять опасную операцию напрямую из UI или LLM-слоя.

Текущая система инструментов включает:

- поиск, чтение, создание и запись файлов;
- удаление, переименование, копирование и перемещение файлов;
- создание папок;
- получение информации о файлах;
- поиск приложений;
- проверку процессов;
- запуск приложений/файлов;
- закрытие приложений;
- открытие HTTP/HTTPS URL.

Для файловых инструментов действует ограничение Workspace. Абсолютные пути вне разрешённой области блокируются.

---

## 8. Пути и Workspace

Jarvis должен оставаться переносимым. Нельзя добавлять жёсткие зависимости вроде `C:\Jarvis\...`.

Пути приложения определяются через `app_paths`. Пользовательские данные находятся отдельно от исходников.

Текущий `tools.paths` дополнительно реализует:

- поиск по Workspace и корню приложения;
- исключение служебных каталогов (`.git`, `__pycache__`, `.venv`, `venv`, `node_modules`, `logs`);
- проверку допустимости найденного пути;
- точное сопоставление имени и stem без обязательного указания расширения;
- fuzzy-поиск имени файла;
- транслитерационное сравнение кириллицы и латиницы;
- разрешение неоднозначных совпадений без автоматического выбора;
- добавление существующего файла в Workspace.

---

## 9. Приложения, ярлыки и процессы

Запуск приложения или файла выполняется без shell-команд через системный Windows-механизм.

Поддерживается запуск объектов из Workspace, а также поиск установленных приложений через ярлыки Windows Start Menu и `PATH`.

Для `.lnk` реализовано разрешение реального executable. Основной механизм использует `win32com`, а отдельный слой совместимости умеет разрешать ярлыки через Windows Shell, если основной механизм недоступен.

При нескольких файлах в Workspace Jarvis не выбирает случайный объект. Он сохраняет список кандидатов и позволяет выбрать вариант по номеру или порядковому слову.

Для нескольких ярлыков одного executable реализована дедупликация по реальному исполняемому файлу.

Закрытие приложения выполняется по реальному executable/процессу и умеет:

- сопоставлять путь executable;
- сопоставлять имя executable;
- проверять command line процесса;
- учитывать имя процесса;
- находить корневые совпавшие процессы;
- собирать дочернее дерево процессов;
- завершать дерево от дочерних процессов к родительскому;
- ждать завершения;
- в совместимом слое использовать `kill()` после таймаута для уже подтверждённых процессов.

Система также пишет подробные снимки процессов до и после закрытия для диагностики.

---

## 10. Алиасы

`core.alias_manager.py` реализует отдельную систему алиасов для:

- приложений;
- файлов;
- папок;
- действий.

Поддерживаются exact-match и fuzzy suggestions. Fuzzy-совпадение не должно автоматически считаться точным.

Для русского текста используется нормализация Unicode, приведение `ё` к `е`, нормализация слов и, при наличии зависимости, `pymorphy3` для морфологической нормализации.

Сохранение предложенного fuzzy-алиаса требует явного подтверждения пользователя.

Алиасы хранятся отдельно от исходников и участвуют в разрешении аргументов инструментов.

---

## 11. Command Router

`services/command_router.py` является центральной точкой выбора способа обработки.

Простые команды могут выполняться напрямую без LLM. Сейчас Router напрямую обрабатывает, в частности:

- запуск приложения/файла;
- закрытие приложения;
- проверку состояния приложения;
- поиск файла;
- чтение файла;
- удаление файла;
- статус Ollama;
- запуск Ollama;
- остановку Ollama.

Составные команды с несколькими распознанными действиями направляются в LLM.

Для контекстных запросов вроде «где находится» Router проверяет наличие явного файлового/папочного контекста, чтобы обычная беседа не превращалась в ошибочный файловый поиск.

Router использует систему алиасов и может предложить сохранить новое название объекта после fuzzy-совпадения.

---

## 12. Выбор инструментов для LLM

`ChatService` не передаёт LLM все инструменты без разбора.

Для каждого сообщения определяется ограниченный набор инструментов на основе:

- явного действия;
- составной команды;
- ключевых слов;
- включённых пользователем инструментов.

Обычная беседа без признаков файловой/программной задачи получает пустой набор инструментов.

Это отдельный уровень защиты от ситуации, когда обычный текстовый диалог внезапно вызывает файловый инструмент.

---

## 13. ToolExecutor и подтверждения

`ToolExecutor` является единой точкой выполнения зарегистрированных инструментов.

Перед запуском он проверяет:

1. существует ли инструмент;
2. включён ли он;
3. разрешён ли он через PermissionManager;
4. корректны ли аргументы;
5. нужно ли подтверждение;
6. какой результат вернул инструмент.

Опасные файловые операции зарегистрированы с обязательным подтверждением.

Инструмент закрытия приложения в текущем registry не требует отдельного подтверждения, поскольку закрытие является отдельным системным действием и текущая реализация использует прямое выполнение через Router/ToolExecutor.

---

## 14. Ollama

Ollama является локальным внешним сервисом.

В текущей реализации:

- Ollama Server проверяется через HTTP API;
- Jarvis может запустить сервер сам;
- Jarvis может остановить сервер, если именно Jarvis его запустил;
- состояние сервера можно проверить из Router/UI;
- можно получить список установленных моделей;
- можно получить список загруженных моделей;
- модель можно загрузить;
- модель можно выгрузить;
- при закрытии Jarvis выгружаются использованные модели;
- уже существующий Ollama Server не должен автоматически завершаться при закрытии Jarvis.

Это сохраняет разделение `Ollama Server` и `загруженная модель`.

Текущая конфигурация `osnova` по умолчанию использует `qwen3-1.7b-no-think:latest`, `thinking=false`, context length 32768 и max tokens 4096, но имя модели является пользовательской настройкой и не должно жёстко вшиваться в новую логику.

## 16. Голосовой ввод

Голосовой ввод в `osnova` уже реализован частично и интегрирован в основной текстовый контур.

Цепочка:

```text
микрофон
  ↓
запись
  ↓
faster-whisper
  ↓
нормализация голосовой команды
  ↓
текстовый ChatService
  ↓
Command Router / LLM
```

Текущая реализация использует `faster-whisper`, загружает модель лениво и выполняет распознавание в фоне через `QThread`.

Поддерживаются:

- выбор микрофона;
- восстановление микрофона по сохранённому имени, а не только по индексу;
- подбор поддерживаемой частоты дискретизации;
- преобразование аудио к 16 кГц;
- русский язык;
- CPU/int8 и другие параметры через конфигурацию;
- VAD;
- beam size 5;
- минимальная длительность записи;
- нормализация распознанных команд.

Нормализатор понимает произнесённые обозначения расширений и пунктуации, например `точка`, `слэш`, `подчёркивание`, `пдф`, `пайтон`, `джейсон`, `экзэ` и другие.

Результат распознавания не обрабатывается отдельным ассистентом. Он передаётся в существующий текстовый контур.

**Пока не реализовано как готовая система:** wake word и TTS. Они остаются будущими функциями.

---

## 17. Голосовые ответы и юмор

TTS пока не является частью текущей рабочей реализации.

Будущая цепочка:

```text
команда
 ↓
обработка
 ↓
финальный текст
 ↓
TTS
```

Юмористические реплики также должны оставаться косметической функцией и не должны влиять на выполнение команд или скрывать ошибки.

---

## 18. Язык ассистента

Пользовательский интерфейс и финальные ответы ориентированы на русский язык.

Внутренний reasoning LLM не требуется искусственно ограничивать русским языком, если это ухудшает качество модели. Проверять русский язык нужно у финального ответа.

---

## 19. Что делать при неоднозначной задаче

Не нужно сразу переписывать проект.

Сначала:

1. определить, что уже реализовано;
2. найти существующий механизм;
3. проверить связанные классы и тесты;
4. определить минимальную недостающую часть;
5. только после этого менять код.

Если без уточнения невозможно безопасно выбрать поведение, задать конкретный вопрос, а не десять вопросов вместо анализа.

---

## 20. Проверка после изменения

После изменения проверить как минимум:

- синтаксис Python;
- импорты;
- соответствующие тесты;
- связанные сценарии;
- отсутствие очевидных регрессий;
- Git diff.

Для UI важно проверять отсутствие блокировки главного потока.

Для Ollama отдельно проверять состояние сервера и состояние модели.

Для голосовой части отдельно проверять цепочку `микрофон → STT → текстовый контур`.

---

## 21. Работа с ветками

`main` — базовая ветка проекта. Она не является автоматически текущей рабочей веткой.

Для текущей разработки используется существующая рабочая ветка. В данном проекте актуальная рабочая ветка пользователя — `osnova`.

Нельзя автоматически переключаться на `main`, создавать новую ветку на каждую задачу или интегрировать изменения в `main` без явного запроса пользователя.

Перед изменением кода проверить актуальную ветку.

---

## 22. Git и коммиты

Коммиты должны описывать конкретное изменение.

Хорошо:

```text
fix: prevent duplicate application launch
feat: add application status tool
docs: sync AI work guide
```

Плохо:

```text
update
fix stuff
changes
```

Не смешивать независимые задачи в одном коммите.

---

## 23. Документация

Документация является частью проекта.

Если важное поведение изменилось, соответствующая документация должна быть синхронизирована с кодом.

Особенно важно не оставлять ситуацию:

```text
код делает A
документация говорит B
```

Для текущего состояния `osnova` при конфликте с устаревшей документацией сначала ориентироваться на код.

---

## 24. Работа двух разработчиков и нескольких ИИ

Важные архитектурные решения должны переноситься из личных чатов в репозиторий:

```text
архитектурные решения → docs/
ТЗ → docs/TZ_JARVIS.md
рабочие правила → docs/AI_WORK_GUIDE.md
проверяемое поведение → tests/
история изменений → Git
```

Контекст не должен существовать только в памяти одного ИИ.

---

## 25. Что ИИ не должен делать

Без явной необходимости и согласования не следует:

- удалять рабочие подсистемы;
- менять основной стек;
- переходить с PySide6 на Electron прямо сейчас;
- менять Python-версию только ради удобства;
- заменять Ollama другим сервером;
- отключать sandbox;
- давать инструментам произвольный shell-доступ;
- встраивать абсолютные пути Windows;
- хранить пользовательские настройки в исходниках;
- менять несколько независимых подсистем в одном коммите;
- считать старую документацию более правильной, чем фактический код;
- автоматически создавать ветку от `main`, если уже существует текущая рабочая ветка;
- автоматически переключаться на `main` для продолжения существующей разработки;
- автоматически делать merge/PR или иным способом интегрировать рабочую ветку в `main` без явного запроса пользователя.

---

## 26. Если код непонятен

Не следует сразу переписывать непонятный код.

Сначала:

```text
найти вызывающий код
    ↓
найти вызываемый код
    ↓
посмотреть типы / интерфейсы
    ↓
посмотреть тесты
    ↓
посмотреть использование в других местах
    ↓
понять поток данных
    ↓
только потом менять
```

---

## 27. Главный принцип проекта

Jarvis должен развиваться от существующей архитектуры, а не постоянно начинаться заново.

```text
прочитать
  ↓
понять
  ↓
найти существующий механизм
  ↓
переиспользовать
  ↓
минимально изменить
  ↓
проверить
  ↓
зафиксировать результат в Git/docs
```
