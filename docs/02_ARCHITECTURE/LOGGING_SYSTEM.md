# Система логирования Jarvis

## Назначение

Jarvis использует расширенное диагностическое логирование для разбора ошибок, зависаний и проблем с инструментами, маршрутизацией команд, LLM, Ollama и управлением процессами Windows.

Логи создаются локально в каталоге `logs/` рядом с Jarvis. Каталог логов не попадает в Git благодаря `.gitignore`.

## Файлы

### `logs/jarvis.log`

Основной подробный журнал.

Сохраняет записи уровня `DEBUG` и выше, включая:

- запуск и остановку Jarvis;
- исключения;
- команды пользователя;
- работу Command Router;
- определение действия и цели;
- работу алиасов;
- вызовы инструментов и их аргументы;
- результаты инструментов;
- подтверждения пользователя;
- подготовку LLM-запросов;
- сообщения и tool calls LLM;
- запросы к Ollama и ответы;
- загрузку и выгрузку моделей;
- поиск, запуск и закрытие приложений;
- сведения о процессах Windows;
- PID, PPID, имя процесса, executable, cmdline, статус и время создания;
- построение дерева процессов;
- порядок завершения процессов;
- ошибки `psutil`, COM, Windows API и сетевых запросов.

### `logs/errors.log`

Только ошибки уровня `ERROR` и выше, включая stack trace для исключений.

Этот файл предназначен для быстрого поиска причины сбоя без необходимости листать весь журнал.

### `logs/events.log`

Журнал событий в формате JSON по одной записи на строку.

Он содержит структурированные данные, которые удобно анализировать программно. В него попадают записи от `jarvis` и его дочерних логгеров.

### `logs/startup.log`

Ранние события запуска, которые могут произойти до полной инициализации приложения.

### `logs/fatal.log`

Данные `faulthandler` для фатальных ошибок Python, включая информацию по потокам.

## Ротация

Основные журналы ограничены размером примерно 10 МБ на файл и хранят до 10 резервных копий. Это предотвращает бесконечное разрастание логов.

## Диагностика закрытия процессов

При `close_application()` дополнительно сохраняется снимок процессов до и после операции. Для найденных кандидатов записываются:

- PID;
- PPID;
- имя процесса;
- полный путь executable;
- командная строка;
- статус;
- пользователь процесса;
- время создания;
- способ сопоставления (`executable_path`, `executable_name`, `command_line` или `process_name`).

Также записываются:

1. исходное имя команды;
2. результат разрешения приложения;
3. путь Workspace/ярлыка;
4. `TargetPath` `.lnk`;
5. найденные процессы;
6. корневые процессы;
7. полное дерево дочерних процессов;
8. порядок `terminate()`;
9. процессы, которые не завершились;
10. итог операции.

## Как использовать для разбора бага

Для бага с Telegram достаточно воспроизвести проблему один раз:

1. Запустить Jarvis.
2. Убедиться, что Telegram запущен.
3. Выполнить `закрой Telegram`.
4. Закрыть Jarvis.
5. Передать содержимое `logs/jarvis.log` и `logs/errors.log`.

По этим данным можно определить, проблема находится в Router, алиасах, Workspace, разрешении `.lnk`, определении `TargetPath`, поиске процесса или завершении дерева.

## Важное замечание

Расширенное логирование намеренно подробное. Оно предназначено именно для отладки локального Jarvis и может содержать текст команд, аргументы инструментов, содержимое LLM-запросов и сведения о запущенных процессах.
