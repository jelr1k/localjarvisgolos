# Документация Jarvis

Документация разделена по назначению. В корне `docs/` находится только этот индекс.

## Источники истины

1. **Код текущей ветки** — фактическое поведение.
2. **Тесты** — проверяемое поведение.
3. **`01_REQUIREMENTS/PROJECT_SPEC.md`** — что Jarvis должен делать сейчас.
4. **`04_STATUS/IMPLEMENTATION_STATUS.md`** — что реально реализовано.
5. **`01_REQUIREMENTS/ROADMAP.md`** — что планируется потом.
6. Остальные документы — специализированный контекст.

Если код и документация расходятся, код не становится неверным только потому, что Markdown написал обратное. Сначала фиксируем фактическое поведение, затем обновляем документацию.

## Что где искать

### 01 — Requirements
Главные требования и долгосрочное направление. Здесь не должно быть нескольких конкурирующих ТЗ.

### 02 — Architecture
Как устроен проект и какие правила соблюдать при изменении кода. `AI_WORK_GUIDE.md` предназначен именно для ИИ-разработчиков.

### 03 — Features
Подробности отдельных подсистем и пользовательских возможностей.

### 04 — Status
Только фактическое состояние реализации. Здесь не хранится полноценное ТЗ.

### 05 — Installation
Зависимости и подготовка окружения.

### 06 — Issues
Отдельные текущие баги, которые требуют самостоятельного исправления. Решённые баги удаляются или переносятся в историю, а не остаются навечно в рабочей документации.

### 07 — Reviews
Исторические ревью и их выводы. Они не являются источником требований. Решения из ревью после принятия переносятся в Requirements/Status/Issues.

## Правило для новых документов

Перед созданием нового Markdown-файла нужно проверить, не относится ли информация к существующему документу. Один факт должен иметь одно основное место хранения.

Не создавать отдельный файл только ради списка из нескольких пунктов, если эти пункты относятся к существующей подсистеме.
