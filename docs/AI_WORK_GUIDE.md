# Руководство для ИИ по работе над Jarvis

**Назначение:** этот документ переносит рабочий контекст проекта в сам репозиторий, чтобы новый ИИ мог продолжить разработку без доступа к предыдущим личным чатам.

**Проект:** Jarvis — локальный текстовый/голосовой ассистент для Windows 11  
**Стек:** Python, PySide6, Ollama, локальные LLM, в будущем Whisper/TTS  
**Репозиторий:** `jelr1k/localjarvisgolos`

---

## 1. Главная идея документа

Предыдущий ИИ мог знать проект из личного диалога пользователя. Новый ИИ этого контекста не имеет.

Поэтому перед началом работы нужно считать репозиторий главным источником технической правды, а этот документ — инструкцией о том, **как читать, изменять и развивать проект**.

Не нужно пытаться восстановить старую переписку. Нужно восстановить состояние проекта по коду, документации, тестам, истории Git и текущей задаче пользователя.

---

## 2. Порядок изучения проекта перед изменениями

Перед существенными изменениями обязательно пройти следующие этапы:

```text
1. Текущая ветка
        ↓
2. README.md
        ↓
3. docs/AI_WORK_GUIDE.md
        ↓
4. docs/TZ_JARVIS.md
        ↓
5. Структура каталогов
        ↓
6. Связанные исходные файлы
        ↓
7. Тесты
        ↓
8. Git diff / последние коммиты при необходимости
        ↓
9. Только после этого изменение кода
```

Если задача касается конкретной системы, сначала изучить **реальную текущую реализацию**, а не писать новую архитектуру поверх предположений.

Например:

- задача про Ollama → сначала `core/ollama_manager.py` и связанные классы;
- задача про приложения → сначала `tools/applications.py`;
- задача про файлы → сначала `tools/` + `security/`;
- задача про маршрутизацию → сначала `services/` и текущий Command Router;
- задача про интерфейс → сначала `ui/`;
- задача про пути → сначала `core/app_paths.py`, `tools/paths.py` и sandbox;
- задача про настройки → сначала `core/config_manager.py` и `config/`.

## 3. Иерархия источников истины

Если информация конфликтует, использовать следующий приоритет:

1. **Фактический код текущей ветки**.
2. **Тесты**, если они проверяют соответствующее поведение.
3. `docs/AI_WORK_GUIDE.md`.
4. `docs/TZ_JARVIS.md`.
5. `README.md`.
6. Старые коммиты, комментарии и исторические документы.
7. Предположения ИИ.

Особенно важно: документация может устареть. Если код явно отличается от документации, сначала проверить, является ли это намеренным изменением. Не следует слепо переписывать работающий код только потому, что старый документ описывает другое состояние.

---

## 4. Что представляет собой Jarvis сейчас

Jarvis — локальное настольное приложение под Windows 11.

Основной стек:

- Python;
- PySide6;
- Ollama;
- локальные языковые модели;
- в будущем Whisper для распознавания речи;
- в будущем локальный TTS.

Уже существующая архитектура в общем виде:

```text
Пользователь
    ↓
UI / ввод
    ↓
Command Router
    ├── простая команда → прямой Tool
    └── сложная команда → LLM
                              ↓
                         Tool Calling
                              ↓
                         ToolExecutor
                              ↓
                    permissions / sandbox
                              ↓
                       реальное действие
                              ↓
                       проверка результата
                              ↓
                       финальный ответ
```

Важно сохранять разделение ответственности между этими слоями.

---

## 5. Уже реализованное не следует без причины переписывать

В текущем проекте уже существуют базовые механизмы:

- автоматическое определение корня приложения;
- переносимость между директориями и дисками;
- пользовательские настройки в `%APPDATA%\\Jarvis\\settings.json`;
- рабочая папка `workspace`;
- sandbox файловых операций;
- базовый `ToolExecutor`;
- разрешения инструментов;
- файловые инструменты;
- инструменты поиска и запуска Windows-приложений;
- проверка состояния процессов;
- базовое управление Ollama;
- загрузка и выгрузка модели;
- потоковый вывод;
- логирование;
- базовые тесты;
- CI-инфраструктура.

Перед добавлением новой функции нужно проверить, не существует ли уже подходящий механизм.

**Запрещённый тип работы:** создать второй параллельный менеджер путей, второй sandbox, второй ToolExecutor или второй менеджер Ollama только потому, что ИИ не нашёл существующий.

## 6. Принцип минимального изменения

При исправлении или добавлении функции менять нужно минимально необходимое количество файлов.

Не следует:

- переписывать большие файлы целиком без необходимости;
- менять архитектуру ради небольшой функции;
- переименовывать десятки классов без причины;
- удалять рабочую логику ради «более красивого» варианта;
- смешивать несколько независимых задач в одном изменении;
- менять формат конфигурации без необходимости миграции.

Если файл большой, предпочтительно изменить конкретный участок и сохранить остальную структуру.

Если архитектурное изменение действительно необходимо, сначала определить:

1. зачем оно нужно;
2. какие компоненты затронет;
3. что сломается;
4. как это проверить;
5. можно ли выполнить изменение поэтапно.

---

## 7. Безопасность файлов и системных действий

Это один из принципиальных элементов проекта.

Файловые инструменты должны работать через существующий sandbox и не должны самостоятельно обходить его.

Нельзя добавлять произвольное выполнение:

```text
cmd.exe
PowerShell
shell=True
```

для обычных пользовательских операций, если для действия уже существует отдельный безопасный инструмент.

Путь должен проходить существующую проверку безопасности.

Любой новый инструмент должен быть встроен в существующую систему разрешений и `ToolExecutor`, а не вызывать опасную операцию напрямую из UI или LLM-слоя.

---

## 8. Пути приложения нельзя делать жёсткими

Jarvis должен быть переносимым.

Нельзя добавлять такие зависимости:

```text
C:\\Jarvis\\...
D:\\Apps\\Jarvis\\...
```

Рабочие пути должны определяться относительно текущего корня приложения или через существующий `app_paths`.

Пользовательские настройки должны оставаться независимыми от места установки и храниться через существующий механизм `%APPDATA%\\Jarvis`.

Пример ожидаемого поведения:

```text
C:\\Jarvis
    ↓ перенос
D:\\Apps\\Jarvis
```

Приложение должно продолжить работать без ручной правки исходников.

---

## 9. Ollama

Ollama является локальным внешним сервисом.

Не следует предполагать, что Ollama установлен в конкретной папке. Поиск/управление должно использовать существующий механизм проекта.

Важно сохранять разделение:

```text
Ollama Server
       ≠
загруженная модель
```

При закрытии Jarvis модель может быть выгружена, но уже запущенный Ollama Server не должен без причины завершаться.

Текущая конфигурация модели может изменяться пользователем, поэтому код не должен без необходимости встраивать конкретное имя модели напрямую.

---

## 10. Работа с настройками

Настройки пользователя не следует хардкодить в исходниках.

Если появляется новая пользовательская настройка:

1. определить значение по умолчанию;
2. добавить его в существующий механизм конфигурации;
3. обеспечить корректную работу при отсутствии старого ключа;
4. при необходимости обновить UI настроек;
5. проверить загрузку и сохранение;
6. не ломать существующие конфиги пользователя.

Особенно это относится к будущим настройкам:

- имени ассистента;
- модели;
- thinking;
- context length;
- wake word;
- режима активации;
- TTS;
- голоса;
- скорости и громкости речи;
- вероятности юмористических реплик.

---

## 11. Работа с Command Router

Command Router должен быть центральной точкой выбора способа обработки пользовательского ввода.

Предпочтительный порядок:

```text
Прямая однозначная команда
        ↓
прямой Tool
```

Если команда требует понимания естественного языка:

```text
Router
  ↓
подходящая модель
```

Если задача сложная:

```text
Router
  ↓
основная LLM
  ↓
Tool Calling
```

Не следует отправлять абсолютно каждую простую команду в большую LLM, если её можно надёжно определить напрямую.

При этом Router **не должен обходить безопасность**. Даже если Router уверен, что нужно удалить файл, действие всё равно проходит через существующие проверки и подтверждение опасной операции.

---

## 12. Работа с несколькими моделями

Будущая архитектура предусматривает возможность выбирать модель по сложности задачи.

Условно:

```text
простая команда
    → router / малая модель

сложная или многошаговая задача
    → основная модель
```

Выбор модели не должен быть жёстко связан с одним конкретным названием модели.

Пользователь должен иметь возможность менять модель через настройки, если соответствующая функция уже предусмотрена архитектурой.

---

## 13. Голосовое управление

Голосовая часть должна строиться поверх существующего текстового контура, а не создавать отдельный независимый ассистент.

Ожидаемая цепочка:

```text
микрофон
  ↓
Whisper
  ↓
текст
  ↓
Command Router
  ↓
существующий механизм обработки
```

Wake word по умолчанию планируется `Jarvis`, но должен быть пользовательской настройкой.

Ожидаются режимы:

- только после wake word;
- обработка каждой распознанной фразы.

По умолчанию предпочтителен безопасный режим с wake word.

---

## 14. Голосовые ответы и юмор

TTS должен озвучивать уже сформированный финальный ответ, а не вмешиваться в выполнение инструментов.

Планируемая цепочка:

```text
команда
 ↓
обработка
 ↓
финальный текст
 ↓
TTS
```

Также планируется небольшая случайная вероятность юмористической реплики. Это косметическая функция и она **никогда не должна влиять на выполнение команды или скрывать ошибку**.

Вероятность должна быть настройкой пользователя. `0%` означает полное отключение.

---

## 15. Язык ассистента

Пользовательский интерфейс и финальные ответы Jarvis должны быть ориентированы на русский язык.

Для будущей LLM-логики желательно разделять:

```text
язык пользовательского ввода → русский
язык финального ответа → русский
язык внутреннего reasoning → может быть автоматическим
```

Если модель имеет отдельный reasoning/thinking-канал, не следует искусственно заставлять reasoning быть русским, если это ухудшает работу модели. Проверять русский язык следует именно у финального ответа.

---

## 16. Что делать, если задача пользователя неоднозначна

Не нужно сразу переписывать половину проекта.

Сначала:

1. определить, что уже реализовано;
2. определить минимальную недостающую часть;
3. проверить связанные классы и тесты;
4. если есть несколько архитектурных вариантов, кратко сравнить их;
5. выбрать вариант, максимально совместимый с текущей архитектурой.

Если без уточнения действительно невозможно безопасно выбрать поведение, задать конкретный вопрос. Не задавать десять вопросов вместо анализа кода.

---

## 17. Проверка после изменения

После изменения нужно проверить как минимум:

- синтаксис Python;
- импорты;
- соответствующие тесты;
- связанные сценарии;
- отсутствие очевидных регрессий;
- Git diff.

Для изменений безопасности желательно добавлять или обновлять тесты.

Для изменения UI нужно проверить, что фоновая операция не блокирует главный поток.

Для изменения Ollama нужно проверить отдельно состояние сервера и состояние модели.

---

## 18. Работа с базовой и рабочей веткой

Git-структура проекта разделяет **базовую ветку** и **рабочую ветку**.

### 18.1. Базовая ветка

`osnova` — это **базовая ветка проекта**, а не ветка, в которой ИИ должен автоматически выполнять каждую задачу.

Она используется как одна из возможных точек, от которой создаются новые рабочие ветки.

Важно:

> **`osnova` не означает «текущая рабочая ветка».**

Нельзя считать `osnova` актуальным состоянием конкретной разработки только потому, что она является базовой веткой.

Если другая рабочая ветка содержит изменения, которых ещё нет в `osnova`, эти изменения являются частью актуального состояния соответствующей разработки.

### 18.2. Текущая рабочая ветка

Рабочая ветка — это ветка, в которой ИИ фактически выполняет изменения для текущего разработчика.

Если у разработчика уже существует рабочая ветка и предыдущие задачи выполнялись в ней, она должна сохраняться как **текущая рабочая ветка** для последующих задач.

Пример:

```text
osnova
  │
  └── feature/tts
          ↑
    текущая рабочая ветка
```

Если разработчик позже говорит:

```text
«Добавь регулировку громкости TTS»
```

ИИ должен продолжить работу в `feature/tts`, если именно она является текущей рабочей веткой.

ИИ должен читать актуальный код из `feature/tts`, включая все изменения, которые уже были сделаны в этой ветке.

**Нельзя автоматически возвращаться к `osnova` только потому, что `osnova` является базовой веткой проекта.**

### 18.3. Если рабочей ветки ещё нет

Если пользователь просит изменить код, но текущая рабочая ветка ещё не определена, ИИ должен:

1. определить базовую ветку проекта;
2. обычно использовать `osnova` как предлагаемую базу;
3. предложить понятное имя рабочей ветки;
4. **получить подтверждение пользователя перед созданием ветки**;
5. только после подтверждения создать рабочую ветку;
6. сделать созданную ветку текущей рабочей веткой;
7. выполнять изменения уже в ней.

Пример:

```text
Пользователь:
«Добавь TTS»

ИИ:
«Рабочая ветка ещё не определена.
Базовая ветка: osnova.
Предлагаю создать feature/tts.
Создать её?»
```

После подтверждения:

```text
osnova
  │
  └── feature/tts
          ↑
    текущая рабочая ветка
```

### 18.4. Не создавать ветку на каждую задачу

Наличие рабочей ветки означает, что она сохраняется между задачами.

Нельзя делать так:

```text
задача 1 → новая ветка
задача 2 → новая ветка
задача 3 → новая ветка
```

если все эти задачи относятся к одной текущей разработке.

Правильный вариант:

```text
feature/tts
   ↑
   ├── задача 1
   ├── задача 2
   ├── задача 3
   └── задача 4
```

Новая ветка создаётся только тогда, когда пользователь явно просит начать отдельную линию разработки или когда существующий рабочий контекст действительно нужно разделить.

### 18.5. Создание новой рабочей ветки

Если пользователь явно просит новую ветку, ИИ должен определить:

- имя новой ветки;
- от какой ветки она должна создаваться.

Возможные варианты:

```text
osnova
  │
  ├── feature/tts
  │
  └── feature/command-router
```

или:

```text
osnova
  │
  └── feature/tts
          │
          └── feature/command-router
```

Если пользователь явно не указал базу новой ветки, ИИ **не должен угадывать**, если выбор может повлиять на состояние проекта.

ИИ должен предложить подходящую базу и получить подтверждение пользователя.

Особенно важно: если текущая рабочая ветка содержит значительные изменения, нельзя автоматически создавать новую ветку от устаревшей `osnova`, если новая задача логически должна продолжать состояние текущей разработки.

### 18.6. После создания новой ветки

После подтверждённого создания новой рабочей ветки она становится текущей рабочей веткой.

Последующие задачи выполняются в ней, пока пользователь явно не попросит:

- переключиться на другую существующую ветку;
- создать новую рабочую ветку;
- вернуться к другой линии разработки.

ИИ не должен самовольно переключать рабочую ветку.

### 18.7. Интеграция изменений в `osnova`

Изменения рабочей ветки не должны автоматически переноситься в `osnova`.

Merge, PR, rebase с целью интеграции или иное обновление `osnova` выполняются **только по явному запросу пользователя**.

До такого запроса рабочая ветка может существовать независимо от `osnova` и содержать более новое состояние конкретной подсистемы.

### 18.8. Анализ без изменения кода

Если задача требует только чтения, анализа, поиска или объяснения и не требует изменения файлов, создание новой рабочей ветки не нужно.

Но если ИИ собирается изменить файлы, он сначала должен определить рабочую ветку согласно правилам выше.

### 18.9. Обязательная проверка перед работой

Перед изменением кода ИИ должен проверить:

```text
1. Какая ветка сейчас checkout/активна?
2. Есть ли уже текущая рабочая ветка для этого разработчика?
3. Требуется ли продолжить работу в ней?
4. Если нужна новая ветка — от какой ветки она должна быть создана?
5. Получено ли подтверждение пользователя на создание новой ветки?
```

Главное правило:

> **Работать нужно с актуальной текущей рабочей веткой, а не автоматически с `osnova`. `osnova` используется как базовая ветка только тогда, когда это действительно выбранная база новой разработки.**

---

## 19. Git и коммиты

Не следует автоматически работать напрямую в `main`.

`main` не следует изменять без отдельного явного указания пользователя.

Другие рабочие ветки не следует изменять без явного указания или без того, чтобы именно эта ветка была текущей рабочей веткой разработчика.

Перед существенной работой полезно проверить:

```bash
git status
git branch --show-current
git diff
```

Коммиты должны описывать конкретное изменение.

Хорошо:

```text
docs: add AI collaboration guide
fix: prevent duplicate Ollama launch
feat: add application status tool
```

Плохо:

```text
update
fix stuff
changes
```

---

## 20. Не смешивать задачи

Если пользователь просит исправить одну проблему, не следует одновременно:

- менять UI;
- переписывать архитектуру;
- обновлять зависимости;
- переименовывать классы;
- менять формат конфигурации;
- делать косметический рефакторинг.

Исключение — если это действительно требуется для основной задачи.

Цель: каждый коммит должен быть понятен другому разработчику и другому ИИ.

---

## 21. Документация тоже является частью проекта

Если архитектура или важное поведение изменились, обновить соответствующую документацию.

Особенно важно не оставлять ситуацию:

```text
код делает A
документация говорит B
```

Если поведение временное или экспериментальное, это нужно явно отметить.

Для новых крупных подсистем желательно создавать отдельный документ в `docs/`.

---

## 22. Как ИИ должен объяснять изменения разработчику

После работы желательно сообщать кратко:

```text
Что изменено
Почему
Какие файлы затронуты
Что проверено
Какой commit создан
Что осталось сделать
```

Не нужно выдавать огромный пересказ каждого изменённого символа.

Если изменён только небольшой фрагмент файла, объяснять именно этот фрагмент.

---

## 23. Работа двух разработчиков с разными ИИ

Это особенно важно для данного проекта.

У каждого разработчика может быть свой чат и свой контекст. Поэтому **контекст не должен жить только в памяти одного ИИ**.

Важные решения нужно переносить в репозиторий:

```text
архитектурные решения → docs/
текущее ТЗ → docs/TZ_JARVIS.md
рабочие правила → docs/AI_WORK_GUIDE.md
важные изменения → Git history
автоматически проверяемое поведение → tests/
```

Если один разработчик принял важное архитектурное решение в личном чате, после утверждения решения его следует зафиксировать в документации или коде.

Таким образом второй ИИ сможет восстановить контекст самостоятельно.

Особенно важно для Git: каждый ИИ должен сначала определить актуальную рабочую ветку конкретного разработчика и продолжать работу в ней, а не предполагать, что `osnova` содержит все последние изменения.

---

## 24. Как начинать новую сессию разработки

Рекомендуемый стартовый запрос для ИИ:

```text
Проанализируй текущую ветку этого репозитория перед изменениями.
Сначала определи текущую рабочую ветку и проверь, нужно ли продолжать работу в ней.
Затем изучи README.md, docs/AI_WORK_GUIDE.md и docs/TZ_JARVIS.md,
после чего структуру проекта и связанные с моей задачей исходники.
Не создавай новую ветку, если уже существует текущая рабочая ветка для этой разработки.
Не переписывай существующую архитектуру без необходимости.
После анализа покажи, какие файлы и компоненты относятся к задаче,
и только потом предложи минимальный план изменений.
```

После этого можно дать конкретную задачу.

---

## 25. Как не потерять контекст между разработчиками

Если решение важно для обоих разработчиков, не оставлять его только в чате.

Пример:

```text
Плохо:
«Мы решили в чате, что wake word будет храниться в config»

Хорошо:
- решение отражено в конфиге;
- код его использует;
- тест проверяет поведение;
- документация описывает правило.
```

Репозиторий должен постепенно становиться самодостаточным источником контекста.

---

## 26. Что ИИ НЕ должен делать

Без явной необходимости и согласования не следует:

- удалять рабочие подсистемы;
- менять основной стек;
- переходить с PySide6 на Electron прямо сейчас;
- менять Python-версию только ради удобства;
- заменять Ollama другим сервером;
- отключать sandbox;
- давать инструментам произвольный shell-доступ;
- встраивать абсолютные пути Windows;
- хранить пользовательские настройки в исходниках;
- менять несколько независимых подсистем в одном коммите;
- считать старую документацию автоматически более правильной, чем фактический код;
- считать собственные предположения фактом;
- автоматически создавать новую ветку от `osnova`, если уже существует текущая рабочая ветка;
- автоматически переключаться на `osnova` для продолжения существующей разработки;
- автоматически делать merge, PR или иным способом интегрировать рабочую ветку в `osnova` без явного запроса пользователя.

---

## 27. Если код непонятен

Не следует сразу переписывать непонятный код.

Сначала:

```text
найти вызывающий код
    ↓
найти вызываемый код
    ↓
посмотреть типы / интерфейсы
    ↓
посмотреть тесты
    ↓
посмотреть использование в других местах
    ↓
понять поток данных
    ↓
только потом менять
```

Старый код может выглядеть странно, потому что за ним стоит ограничение, которое не видно в одном файле. Люди любят оставлять такие сюрпризы в проектах. ИИ не обязан продолжать эту традицию.

---

## 28. Главный принцип проекта

Jarvis должен развиваться **от существующей архитектуры**, а не постоянно начинаться заново.

Правильный подход:

```text
прочитать
  ↓
понять
  ↓
найти существующий механизм
  ↓
переиспользовать
  ↓
минимально изменить
  ↓
проверить
  ↓
зафиксировать результат в Git/docs
```

Если новый ИИ после чтения этого документа всё равно не понимает конкретную часть проекта, следующий источник информации — **сам код и Git-история**, а не попытка угадать, что имел в виду предыдущий ИИ.

---

## 29. Критерий хорошей работы ИИ

Хорошее изменение — это не самое большое изменение и не самое «красивое» с точки зрения ИИ.

Хорошее изменение:

- решает поставленную задачу;
- сохраняет существующую функциональность;
- не нарушает sandbox и безопасность;
- не создаёт дублирующих механизмов;
- понятно другому разработчику;
- проверяемо тестами или конкретным сценарием;
- отражено в Git;
- при необходимости отражено в документации;
- не требует знания личного чата предыдущего разработчика.
