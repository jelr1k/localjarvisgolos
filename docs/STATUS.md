# Статус разработки Jarvis

**Дата обновления:** 2026-09-15  
**Ветка:** `satichik-dev`  
**Связанный документ:** `docs/TZ_JARVIS.md`

Этот документ фиксирует фактическое состояние реализации на текущем этапе. Он дополняет ТЗ и не заменяет его.

## 1. Command Router — реализовано

Пользовательские сообщения проходят через `Command Router` до обращения к LLM.

Реализованы прямые сценарии для команд, которые можно выполнить без генерации ответа основной моделью, включая запуск/закрытие приложений, поиск файлов, чтение файлов и другие поддерживаемые действия.

Для составных команд Router не выполняет только первый найденный шаг и не обрывает обработку. Если запрос содержит несколько действий, он передаёт задачу дальше в LLM Tool Calling.

## 2. Разделение обычного чата и tools — реализовано

Обычный текстовый диалог не получает весь набор инструментов.

Для задачи формируется ограниченный набор tools, соответствующий пользовательскому запросу. Это снижает вероятность случайного вызова файловых или системных инструментов моделью.

## 3. Составные команды и Tool Calling — реализовано

Поддерживается цепочка:

```text
Пользователь
    ↓
Command Router
    ↓
определение составной задачи
    ↓
LLM + необходимые tools
    ↓
tool call
    ↓
ToolExecutor
    ↓
результат инструмента
    ↓
следующий tool call при необходимости
    ↓
финальный ответ
```

Для разных действий инструменты объединяются. Например:

```text
«Найди файл tool_test.txt, прочитай его и перескажи своими словами»
```

формирует набор:

```text
search → search_files
read   → read_file
```

То есть модель получает одновременно `search_files` и `read_file` и может выполнить оба шага последовательно.

## 4. Multi-round Tool Calling — реализовано

`GenerationWorker` поддерживает несколько последовательных раундов Tool Calling.

После получения `tool_call`:

1. вызов передаётся в `ToolExecutor`;
2. результат инструмента добавляется в контекст;
3. модель получает возможность продолжить задачу;
4. цикл повторяется до финального ответа или достижения ограничения раундов.

Установлено ограничение в 5 последовательных раундов для защиты от бесконечного tool-call цикла.

## 5. Безопасность Tool Calling — реализовано

`GenerationWorker` передаёт `ToolExecutor` только те инструменты, которые были разрешены для конкретного запроса.

Таким образом, даже если модель попытается вызвать инструмент, которого нет в текущем наборе tools, он не считается разрешённым для этого запроса.

Существующие проверки разрешений, sandbox и подтверждения опасных операций сохраняются.

## 6. Работа с файлами — реализовано

Поддерживаются отдельные сценарии поиска и чтения файлов.

При обычном чтении файла пользователю показывается содержимое без обязательного вывода полного системного пути.

При запросе местоположения файла путь может быть показан явно.

Проверенный сценарий:

```text
Найди файл tool_test.txt, прочитай его и перескажи своими словами
```

Файл был найден, прочитан, его содержимое передано модели, после чего Jarvis сформировал итоговый ответ.

## 7. Логирование — реализовано

Для диагностики инструментальных задач доступны логи, позволяющие проследить:

- сообщение пользователя;
- результат маршрутизации;
- выбранные tools;
- начало каждого раунда генерации;
- вызовы инструментов моделью;
- результаты инструментов;
- завершение или ошибку генерации.

Это позволяет отдельно диагностировать Router, выбор tools, ToolExecutor и LLM.

## 8. Что ещё остаётся по ТЗ

Следующие крупные этапы остаются в работе:

- полноценная маршрутизация между несколькими моделями;
- локальное распознавание речи через Whisper или совместимое решение;
- wake word;
- полноценное голосовое управление;
- локальный TTS и голосовые настройки;
- настраиваемая вероятность юмористических ответов;
- сборка и проверка полноценного `.exe`;
- финальная проверка переносимости и установки зависимостей;
- возможный переход интерфейса на Electron.

## 9. Текущий результат этапа

Базовая архитектура Command Router + Tool Calling теперь работает не только для одиночных инструментальных команд, но и для составных задач с несколькими действиями.

Ключевой проверенный сценарий:

```text
найти файл
    ↓
прочитать файл
    ↓
получить содержимое
    ↓
сформировать ответ пользователю
```

Следующий этап развития — улучшение выбора моделей и переход к полноценному голосовому интерфейсу, после чего можно переходить к упаковке Jarvis в конечную пользовательскую сборку.
