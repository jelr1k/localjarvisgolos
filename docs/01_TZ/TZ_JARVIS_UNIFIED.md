# Jarvis — единое ТЗ проекта

**Версия документа:** 1.3  
**Дата обновления:** 2026-09-17  
**Проект:** локальный голосовой/текстовый ассистент Jarvis для Windows 11  
**Стек текущей реализации:** Python, PySide6, Ollama, локальные LLM, faster-whisper  
**Репозиторий:** `jelr1k/localjarvisgolos`  
**Основная ветка текущей разработки:** `osnova`

> **Назначение документа:** единое ТЗ, объединяющее фактическое состояние текущей реализации Jarvis и целевое направление развития проекта.
>
> Документ разделяет уже реализованные возможности, задачи текущего этапа и перспективные требования. Перспективные требования не считаются реализованными только потому, что описаны здесь.

## 0. Общая концепция

Jarvis должен развиваться из локального голосового/текстового помощника и лаунчера в полноценного локального AI-оператора компьютера.

Основная идея: пользователь формулирует задачу обычным языком или голосом, после чего Jarvis определяет необходимое действие, проверяет разрешения и выполняет его с минимально необходимым использованием ресурсов.

Jarvis является прежде всего локальным приложением для управления ПК. Настройки, история, память, разрешения и другие пользовательские данные по возможности должны оставаться локально на компьютере.

### Основные принципы

- локальная работа;
- минимальное потребление CPU, RAM и VRAM;
- управление естественным языком и голосом;
- детерминированные действия без LLM там, где LLM не нужна;
- Command Router как первый уровень обработки команды;
- отдельная система разрешений, не зависящая от решения LLM;
- широкая настройка через UI;
- модульность;
- расширение доступа к компьютеру только вместе с системой доверия и разрешений;
- отсутствие необходимости редактировать исходный код или JSON для обычной настройки;
- возможность расширять функциональность без переписывания ядра.

# 1. Архитектура и текущий статус

## 1.1. Текущая архитектура — ГОТОВО

В ветке `osnova` реализованы базовые архитектурные компоненты:

- автоматическое определение корня Jarvis;
- `Workspace`, определяемый относительно расположения приложения;
- пользовательские настройки и алиасы;
- автоматические базовые алиасы для объектов Workspace;
- живой `WorkspaceIndex`;
- единый resolver для разрешения объектов Workspace;
- sandbox и безопасная работа с путями;
- файловые инструменты;
- инструменты управления приложениями и Windows-ярлыками;
- Command Router;
- ограниченный tool scope для конкретного запроса;
- многораундовый Tool Calling;
- управление Ollama Server и моделью из UI;
- расширенное логирование;
- тесты ключевых компонентов.

## 1.2. Command Router — ГОТОВО

Базовая схема:

```text
Пользовательский ввод
        ↓
Command Router
        ├─ простая однозначная команда → прямой инструмент
        └─ сложная/составная задача → LLM + разрешённые tools
```

Обычный разговор не должен получать полный набор системных и файловых инструментов.

Простые детерминированные команды не должны загружать LLM только ради определения объекта.

Для соответствующих команд запуска и удаления `Command Router` сначала использует `WorkspaceIndex`.

Команды закрытия и проверки состояния приложения используют отдельную процессную логику, поскольку наличие файла в `Workspace` не означает наличие соответствующего процесса.

## 1.3. Tool Calling — ГОТОВО

`GenerationWorker` поддерживает до 5 последовательных раундов Tool Calling. После каждого вызова результат возвращается модели для продолжения задачи или формирования финального ответа.

LLM не должна самостоятельно выполнять системные действия вне разрешённого набора инструментов.

## 1.4. Единый каталог пользовательских команд — ТРЕБОВАНИЕ

Проект должен иметь единый справочник всех пользовательских действий Jarvis, независимо от того, каким уровнем они выполняются.

Справочник хранится в:

`docs/03_FEATURES/COMMAND_REFERENCE.md`

Он должен описывать как минимум:

- название действия;
- назначение;
- примеры естественных формулировок;
- основные синонимы и варианты формулировки;
- способ обработки: `Command Router`, `LLM + Tools`, комбинация уровней или план;
- текущий статус реализации.

Справочник не ограничивается командами `Command Router`. В него должны попадать также действия, доступные через инструменты LLM, составные сценарии и планируемые возможности.

### Правило архитектуры команд

Если пользовательская команда является простой, однозначной и детерминированной, Jarvis должен по возможности выполнять её через `Command Router` без запуска LLM.

Если задача требует интерпретации естественного языка, нескольких последовательных действий, анализа результата или выбора между несколькими инструментами, она может передаваться локальной LLM с ограниченным набором разрешённых tools.

Наличие LLM-инструмента само по себе не означает, что простой сценарий должен обязательно проходить через LLM.

### Синхронизация

При добавлении нового пользовательского действия необходимо синхронно проверить и при необходимости обновить:

1. `COMMAND_REFERENCE.md`;
2. алиасы и синонимы в Alias Manager;
3. `Command Router`, если действие должно выполняться детерминированно;
4. доступные tools и Tool Calling, если действие выполняется через LLM;
5. ТЗ и статус реализации, если изменение влияет на архитектуру.

Цель: избежать ситуации, когда команда существует в коде или tool-системе, но разработчик не знает о ней из-за отсутствия единого списка.

# 2. Workspace, доступ к ПК и безопасность

## 2.1. Текущий Workspace

На текущем этапе `Workspace` является границей безопасной работы Jarvis.

Все файловые операции и запуск объектов по умолчанию должны выполняться внутри автоматически определяемого Workspace. Путь Workspace должен оставаться переносимым при перемещении Jarvis между дисками.

Фактическое содержимое `Workspace` является источником истины для существования объектов, а пользовательская команда, STT и ответ LLM сами по себе не создают объект.

## 2.2. Будущее расширение доступа

Workspace является текущей защитной моделью разработки, но не обязательно конечным ограничением Jarvis.

В перспективе Jarvis должен уметь работать с объектами всего компьютера, однако расширение доступа должно сопровождаться отдельной системой разрешений и доверия.

## 2.3. Система разрешений — ПЛАН

Система разрешений должна быть независимой от LLM.

Предполагаемые уровни:

- безопасные действия — выполняются автоматически;
- потенциально опасные — требуют подтверждения;
- критические — требуют повышенного подтверждения или могут быть запрещены полностью.

LLM не должна самостоятельно определять собственные права.

# 3. Работа с файлами

## 3.1. Текущее состояние

Файловая подсистема реализована внутри разрешённого Workspace.

Для подключённых к единому resolver сценариев используется фактическое содержимое Workspace и `WorkspaceIndex`.

Поддерживается неоднозначность, когда существует несколько реальных совпадений.

## 3.2. Единый resolver — ОСНОВНАЯ ЧАСТЬ РЕАЛИЗОВАНА

`tools.paths.resolve_workspace_path()` является общей точкой разрешения объектов внутри Workspace для новых сценариев.

Реализовано:

- поиск по фактическим объектам Workspace;
- поиск без обязательного расширения;
- нормализация регистра и разделителей;
- пользовательские и автоматические алиасы;
- контролируемое нечёткое сопоставление;
- сохранение неоднозначных совпадений;
- защита от выхода за пределы Workspace.

Остаётся расширить использование resolver на все файловые операции и закрыть дополнительные regression-сценарии.

Whisper/STT не должен самостоятельно решать, существует ли файл.

## 3.3. Автоматические алиасы и Workspace Index

`core/workspace_index.py` поддерживает живой индекс объектов Workspace.

Индекс:

- сканирует фактическое содержимое Workspace;
- учитывает файлы, папки и запускаемые объекты;
- связывает объекты с именами и алиасами;
- поддерживает exact и контролируемое fuzzy-сопоставление;
- возвращает несколько кандидатов вместо случайного выбора;
- обновляется при обращении к индексу.

Для известных приложений поддерживаются устойчивые русские варианты, например `Steam → стим`, `Telegram → телеграм`, `Discord → дискорд`, `Minecraft → майнкрафт`.

Автоматический перевод неизвестных названий не выполняется.

Полное разделение хранения автоматических и пользовательских алиасов в Alias Manager и полный жизненный цикл переименования/перемещения ещё требуют доработки.

## 3.4. Добавление файлов в Workspace через UI — ГОТОВО

Вкладка «Алиасы» предоставляет интерфейс Workspace с:

- выбором файла через `QFileDialog`;
- drag-and-drop файла из Проводника.

После добавления файл копируется в Workspace без автоматической перезаписи существующего объекта, отображается в интерфейсе и получает базовые алиасы.

Операции проходят через существующий sandbox-путь Workspace.

## 3.5. Целевые файловые возможности

В перспективе Jarvis должен поддерживать:

- поиск;
- чтение;
- анализ;
- создание;
- открытие;
- редактирование;
- переименование;
- перемещение;
- удаление;
- запись указанного пользователем текста;
- генерацию текста и сохранение результата в файл;
- поиск по содержимому;
- работу с папками.

# 4. Запуск приложений, игр и процессов

## 4.1. Запуск

Jarvis должен уметь запускать пользовательские приложения, игры и другие объекты Windows.

Должны поддерживаться `.exe`, `.lnk`, `.url`, `.bat`, `.cmd` и другие подходящие объекты.

Пользователь должен иметь возможность обращаться к объекту по понятному имени или алиасу без обязательного указания расширения.

## 4.2. Закрытие

Jarvis должен уметь:

- находить связанные с приложением процессы;
- корректно закрывать приложение;
- при необходимости завершать процесс, если это разрешено;
- работать с приложениями независимо от способа их запуска;
- избегать завершения несвязанных системных процессов.

Процессная логика является отдельной от `WorkspaceIndex`: индекс определяет объекты Workspace, а закрытие работает с фактическими процессами.

# 5. Выполнение CMD и PowerShell

Jarvis должен в перспективе уметь выполнять команды через Windows CMD, PowerShell и другие подходящие системные интерфейсы.

LLM может помогать интерпретировать сложный запрос, но фактическое выполнение должно проходить через Command Router, разрешённые инструменты и Permission System.

# 6. Голосовой ввод

## 6.1. Текущее состояние — ЧАСТИЧНО ГОТОВО

Локальный STT реализован через `faster-whisper`.

Текущая конфигурация:

- модель `small`;
- `device="cpu"`;
- `compute_type="int8"`;
- язык `ru`;
- 16 kHz;
- `beam_size=5`;
- `vad_filter=True`;
- ленивая загрузка;
- автоматический ресэмплинг к 16 kHz.

Распознанный текст передаётся в существующий путь обработки сообщений и далее в Command Router/LLM.

Whisper отвечает только за STT. Проверка существования файлов и приложений выполняется соответствующими подсистемами.

## 6.2. Не реализовано

- Wake word, по умолчанию `Jarvis`;
- постоянный режим ожидания;
- TTS.

## 6.3. Сетевая особенность

В пользовательском окружении локальный прокси Happ может передавать Python/Hugging Face адрес `127.0.0.1:10808` как SOCKS4-прокси, что вызывает `Unknown scheme for proxy URL`.

Это относится к сетевому окружению, а не к модели Whisper.

# 7. UI и управление моделью

Текущий UI построен на PySide6.

Реализованы управление Ollama Server и моделью из интерфейса, а также отображение статистики генерации и диагностического состояния.

Освобождение модели при закрытии Jarvis должно происходить без обязательной остановки Ollama Server.

---

# 8. Логирование и тестирование

Реализовано расширенное логирование ключевых компонентов, включая Command Router, ToolExecutor, LLM/Ollama и управление процессами.

В проекте присутствуют unit/regression-тесты ключевых компонентов и GitHub Actions workflow для автоматического запуска тестов.

Наличие тестов в репозитории не означает, что конкретный набор тестов был успешно выполнен при каждом изменении документации. Фактический результат тестового запуска должен проверяться отдельно.
