# Jarvis — автоматические алиасы и индекс Workspace

**Статус:** ОСНОВНАЯ ЧАСТЬ РЕАЛИЗОВАНА  
**Основное ТЗ:** `docs/TZ_JARVIS.md`  
**Единое ТЗ:** `docs/TZ_JARVIS_UNIFIED.md`  
**Ветка:** `osnova`

## 1. Цель

Автоматически находить объекты `Workspace` по их реальным именам и алиасам без необходимости вручную создавать базовый алиас для каждого объекта.

Источником истины для существования объекта является фактическое содержимое `Workspace`.

## 2. Что уже реализовано

### 2.1. Workspace Index

В `core/workspace_index.py` реализован живой `WorkspaceIndex`, который:

- сканирует фактическое содержимое `Workspace`;
- учитывает файлы, папки и запускаемые объекты;
- хранит реальные имена и пути объектов;
- поддерживает автоматические и пользовательские алиасы;
- выполняет нормализацию регистра и разделителей;
- поддерживает контролируемое нечёткое сопоставление;
- сохраняет список совпадений при неоднозначном результате;
- не создаёт объект только на основании текста команды.

Индекс обновляется при обращении к нему, поэтому изменения содержимого `Workspace` учитываются без отдельного ручного импорта каждого объекта.

### 2.2. Единый resolver

`tools.paths.resolve_workspace_path()` использует `WorkspaceIndex` и является общей точкой разрешения путей для новых сценариев, которым требуется найти объект внутри `Workspace`.

Resolver:

- принимает имя без расширения;
- учитывает реальные объекты `Workspace`;
- поддерживает алиасы;
- допускает контролируемое fuzzy-сопоставление;
- возвращает неоднозначный результат отдельно, а не выбирает случайный объект;
- не позволяет выйти за границы `Workspace`.

### 2.3. Command Router

`Command Router` использует `WorkspaceIndex` для соответствующих прямых команд, в частности для запуска и удаления объектов.

Целевая схема фактически используется для простых команд:

```text
Пользовательская команда
        ↓
Command Router
        ↓
Workspace Index
        ├─ один объект → прямое выполнение
        ├─ несколько объектов → список кандидатов
        └─ нет подходящего объекта → дальнейшая обработка
```

Однозначный запуск объекта не требует обращения к LLM только ради определения его имени.

Операции закрытия и проверки состояния приложения остаются процессными операциями и не должны разрешаться только через индекс файлов `Workspace`.

## 3. Автоматические базовые алиасы

Для объекта используются его реальные имя, stem и связанные варианты, доступные через индекс.

Примеры:

- `Steam.url` → `steam`;
- `Telegram.lnk` → `telegram`;
- `Geometry Dash.exe` → `geometry dash`;
- `Minecraft.lnk` → `minecraft`.

Расширение файла не требуется в пользовательской команде.

## 4. Русские алиасы

Для распространённых приложений и игр используется контролируемый словарь устойчивых русских вариантов.

Примеры поддерживаемых вариантов:

- `Steam` → `стим`;
- `Telegram` → `телеграм`;
- `Discord` → `дискорд`;
- `Minecraft` → `майнкрафт`;
- другие названия могут добавляться в словарь при наличии надёжного общеупотребительного варианта.

Автоматический перевод неизвестных названий не выполняется, чтобы не создавать ложные совпадения.

## 5. Неоднозначность

Если одному запросу соответствуют несколько реальных объектов, Jarvis не выбирает объект случайно.

Пример:

```text
Найдено несколько объектов:
1. Steam.url
2. Steam.exe
```

Пользователь должен выбрать нужный вариант.

## 6. Пользовательские алиасы

Пользовательские алиасы должны оставаться независимыми от автоматической индексации.

Переименование, перемещение или пересканирование объекта не должно удалять пользовательский алиас только потому, что автоматически вычисленное имя изменилось.

Полное разделение хранения и отдельное отображение автоматических и пользовательских алиасов остаётся задачей, если конкретная реализация Alias Manager ещё не обеспечивает это полностью.

## 7. Что ещё требуется

Остаются следующие задачи:

- завершить единое хранение автоматических и пользовательских алиасов в Alias Manager;
- обеспечить корректное обновление автоматических алиасов при переименовании и перемещении;
- расширить автоматическую индексацию на все способы появления объектов в `Workspace`;
- при необходимости расширить словарь русских общеупотребительных названий;
- добавить отдельные regression-тесты для переименования, перемещения и удаления объектов.

## 8. Ограничения

Автоматические алиасы не обходят sandbox, `Workspace` или систему разрешений.

LLM не является источником истины о существовании файла или приложения. Для объектов `Workspace` существование подтверждается фактическим содержимым рабочего каталога.

## 9. Будущее расширение

В дальнейшем механизм может учитывать:

- распространённые сокращения;
- ошибки STT;
- морфологические формы русского языка;
- историю успешных команд;
- дополнительные источники устойчивых названий.

Такие расширения не должны превращать неоднозначный или неподтверждённый вариант в автоматическую команду без достаточной уверенности.
